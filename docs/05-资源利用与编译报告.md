### 1.2 ⚠️ 面积为什么从 958 LE 涨到 1201 LE（**ERR-019 阶段的历史记录，别当成退步**）

第 2 阶段仿真抓出的 **ERR-019**（`srl8` 移位方向反了）修正之后，面积从
**958 LE（75%）涨到 1201 LE（95%）**，Fmax 从 42.24 MHz 降到 41.39 MHz。

原因不是"代码写啰嗦了"，而是**旧的错误方向让综合器白捡了便宜**：

* 错误的**左移**会把零片形状里**低列**的格子推出边界 → 锚点列 ≥ 3 的那几路输出
  恒为 0 → Quartus 把这些逻辑**常量折叠**掉，整片移位网络被剪掉一大块；
* 正确的**右移**必须把格子搬到高列，**每个锚点列都真的要用** → 无法折叠。

验证：把方向改回错误的写法重建，面积立刻回到 **967 LE**；再改回正确写法又是
**1201 LE**；连"位序反转→左移→再反转"的等价改写**也是 1201 LE**（等价函数综合后
就是同一张网表）→ 证明这个代价是**方向正确本身**带来的，不是写法问题。

**处置**：接受 95%（仍能放下，余量 69 LE，fitter 0 error，`.pof` 正常生成），并把它
写进报告"已知不足"。**绝不能为了面积好看而保留一个把零片画错列的 bug。**

> ⚠️ **2026-10-08/09 后续更正（数字已变，结论不变）**：ERR-019 之后又修了 **ERR-020**
> （方向与移动请求同拍锁存，+1 LE → **1202 LE**）与 **ERR-021**（成功判据改为整帧画面比较，
> → **1187 LE**）、**ERR-023/ERR-024**（去鬼影 + `shuf_seen`，→ **1191 LE**）、
> **结算画面改版**（`WIN_MASK` 换笑脸 + 3 位 `endflash_cnt`，→ **1188 LE**）、

> **第 9 工作阶段**（绿对勾 + 消抖 40 ms，→ **1210 LE**；**A2/S1 第二关图案库，→ 1242 LE**）。
> **第 11 工作阶段**（异形零片 + ERR-032 条件相减 → **1254 LE**；再叠加 **ERR-033 两拍流水 +

> 当前实测 **1234 / 1270 LE（97%）**、余量 **36 LE**、**Fmax 49.02 MHz（距 50 MHz 差 0.398 ns）** ——
> 判据改整帧比较时"面积不升反降"；其余改动多为 **±6 LE 以内波动**，

### 4.1 两条守卫的作用范围（**教训**）

* 第一道守卫只能看到**你列出的端口** → **抓不到"漏列端口"**（ERR-002 正是钻了空子）；
* 因此加了第二道：解析 `rtl/<top>.vhd` 的 **entity 端口列表**，任何未列入的端口**直接报错退出**。
* **守卫自身也要被审查**：第二道守卫第一版匹配到了注释里的 "is" 一词，只解析出 1 个端口 ——
  **一个少报的守卫比没有守卫更危险**（它看起来检查过了）。修正为**先剥注释再解析**。

| 最差路径（2 条） | ① `clk_gen:u_clk\|d_press[4] → puzzle_ctrl:u_puzzle\|frame_g[7]`（20.065 ns）＝**复位网络**：`o_rst` 从按键消抖寄存器一路组合过来，接到每个寄存器的同步复位端；② `puzzle_ctrl\|pos[13] → bad_a`（20.023 ns）＝渲染行的"整帧判据"那一级 |
| **功能风险** | **低** —— 所有外设都是**人机接口**（按键 / 点阵 / 数码管 / 蜂鸣器），真实数据速率 ≤ 200 Hz；复位晚 0.4 ns 生效无任何可观察后果。但仍**如实记为"未满足约束"** |

**已做的流水化**（关键路径 26 ns → 19.4 ns，中间过程最好 19.4 ns）：

| 序 | 原关键路径 | 处置 |
|---|---|---|
| 1 | `disp_format` 的 `t/10`、`t mod 10` 推出 **`lpm_divide`** 进位链（26 ns） | 换成 **64 项查找表**，该处除法器消失 |
| 2 | `pos → o_solved → 音效多路器 → buzz` | 状态标志与音效码各**加一级寄存器** |
| 3 | `sel → 锚点多路 → 边界比较 → 启动检查引擎` | 移动请求**两拍流水** |
| 4 | `pos → 相减 → 范围比较 → row_mask 移位` | **行号加一级寄存器**；`srl8` 由逐位循环改 **7 路 mux 树** |
| 5 | **`pos[12] → frame_g[53]`（行渲染一行到底，slack 仅 +0.023 ns）** | **ERR-033：把"算一行"与"并入帧 + 整帧判据协议"拆成两拍** |
| 6 | **`mv_anchor → 夹紧 → 边界比较 → chk_shp`（slack −0.190 ns）** | **ERR-033b：移动校验再拆一拍（夹紧后的锚点先进寄存器）** |
| 7 | **渲染器与重叠检查引擎各有一份 `row_mask/srl8`** | **`AUTO_RESOURCE_SHARING ON`（qsf/生成器一行）→ 共用同一份移位网络** |

> ⚠️ **第 11 工作阶段的时序账（都实测，重跑一致）**：
> 第二关零片改成异形后，散落里的 `x mod ch` 除数不再恒定（原来是"全部 2×2"→ 常量，
> 被综合器折叠）→ 长出两个**变除数除法器**，整机 Fmax 从 44.77 掉到 **36.68 MHz**
> （TNS **−926 ns**）。这是**本轮唯一一次功能改动引起的时序回退**，见 `docs/06` **ERR-032**；
> 修法是 `x ≤ 7`、`ch ≥ 4` 时 `x mod ch ≡ 一次条件相减`（**候选序列逐拍完全相同**）→
> 50.06 MHz。再叠加 ERR-033 的两拍流水与资源复用 → **51.44 MHz / 1200 LE**。
> **随后全项目审计修复（ERR-035~038）又占了 34 LE、Fmax 回到 49.02 MHz** ——
> 最终版**保留了修复**（B1 的 2 Hz 闪烁、B8"不可再选择"都是**明文基本要求**，
> 优先于那 2% 的时序），这一点在报告里要如实写。
>
> ⚠️ **为把 Fmax 拉回 50 而做过的补救尝试（全部比现状差，别再试）**：
> `ERR-040` 把 `cov` 比较挪到第二拍 → 1242 LE / **41.67 MHz**；
> `ERR-041a` 复位在 `puzzle_ctrl` 内打一拍 → 1252 LE / **46.15 MHz**；
> `ERR-041b` 复位在 `clk_gen` 源头打一拍 → 1234 LE / **44.49 MHz**；
> fitter `SEED` = 2 / 3 / 5 / 7 → **43.17 / 46.27 / 37.99 / 48.73 MHz**（默认 seed 的 49.02 最好）。
> 另有两条工具开关**实测无效**：`REMOVE_REDUNDANT_LOGIC_CELLS ON`（面积一个没动）、
> `OPTIMIZATION_TECHNIQUE=AREA`（9.1 不接受，`map.rpt` 仍显示 Balanced）。
>
> ✅ **余量**：当前 **1234 / 1270 LE（97%）**，余量 **36 LE**；"引擎内容更新率提速（+76 LE）"
> 依旧不做（闪烁只与扫描率有关），**A3 方向随机 / A4 旋转**仍不做（理由已改为
> "收益不抵复杂度"，不再是"装不下"）。
