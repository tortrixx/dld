### 1.4 零片散落与判定的读法（B5/B8/B9 的裁决）

原文只说"位置随机，但不能重叠"（B5）、"拼图成功（位置和形状与初始拼图一致）"（B9）。
由此确定**唯一自洽语义**：

- 预览时显示的完整图案 = **零片目标位置的并集**；
- 零片散落时**必须偏离**目标位置（否则一开局就"已完成"）；
- **成功** = 全部零片已按"确认"锁定 **且** 零片**并集 == 目标图案**（即**画面逐格一致**）。

> ⚠️ **2026-10-08 更正（ERR-021）**：原稿把判据写成"每块零片回到**它的**目标锚点"
> （即每块锚点 == 写死的 `L1_TGT*` / `L2_TGT*`）。**上板实测：第一关能过，第二关即使拼对，
> 按"确认"仍然出"叉"。** 根因是**同一幅画面可以有多种等价摆法**：
> 第二关四块是**完全相同**的 2×2 方块，填满 4×4 目标共有 **4! = 24 种**摆法，
> 画面逐格相同，而"锚点判据"只认其中 1 种 → **23/24 ≈ 96% 的"拼对"被判失败**；
> 第一关 4×3 矩形也有 **2 种**等价铺法（`.ref/solve_l1.py` 早就枚举出来了），
> 锚点判据只认 1 种 → 命中率只有 1/2。
> **B9 的原话是"位置和形状与初始拼图一致"——指的是玩家看到的"画面"，
> 不是"哪一块放到哪个编号的位置"。** 因此判据改为**零片并集 == 目标图案**（整帧画面逐格比较）：
> 它覆盖全部等价摆法，同时**不会**放宽成"随便摆都成功"（四块原地锁定、画面不对仍然判失败）。
> 复现/回归：`sim/rounds/puzzle_ctrl/r10.json`（修复前 16/17，断言 ⑭ ❌）→ `r11.json`
> （修复后 17/17，断言 ⑭ ✅）；断言表见 `docs/03`，根因与修法见 `docs/06` 的 **ERR-021**。
> `L1_TGT*`/`L2_TGT*` 常量仍保留，但**已不再是成功判据**，仅用于 `check_geometry.py` 与文档。

> ⚠️ **2026-10-08 再更正（ERR-023）**：上面的判据要能成立，前提是**喂给引擎的目标图案在
> 对局态也是真实的**。而顶层 `puzzle_top` 原来在对局态把 `i_target` 置零
> （`tgt_play <= tgt_mask when (预览/自检) else (others => '0')`，当年是为 ERR-013
> "别让红色虚影盖住零片"）。判据是"零片并集 == `i_target`"，`i_target` 一旦为 0，
> **该判据永远不可能成立** —— 上板表现就是"第一关拼对了按确认仍出叉"。
> 现改为：① **真实目标图案 `tgt_mask` 恒接给引擎 `i_target`**（判据需要它）；
> ② **"不画红色虚影"改由引擎自己保证**（引擎帧只在 `S_PLAYING` 显示，对局态本就不该有虚影，
> 那段鬼影逻辑本来就是"靠置零活着"的死代码）；③ 预览仍由顶层用 `prev_row` 显示完整图案，
> **对局画面与以前完全一致**（只有零片、没有虚影）。
> 可执行 A/B：整机 `r12` **8/12**（三块准确拼回目标锚点后状态机却是"失败"）→ `r14` **12/12**。
> 详见 `docs/06` ERR-023 与 `docs/03` §5.3。

> 这是本设计**最关键的语义裁定**，全部逻辑与仿真断言都按此写。若老师另有口径，改这一处即可。

### 3.2 ⚠️ 三个必须写进设计的硬件事实

1. **点阵绿列 COLG0~COLG7 与 LD8~LD15 复用同一批引脚（38~45）**，
   VGA 又与 LD8~LD15 复用（137~144）。
   → **本设计不使用 16 个 LED**，点阵 + 数码管已足够表达全部要求；
   **一旦要点亮 LED 就必然与点阵绿列抢引脚**（点阵将失去绿色）。这是硬冲突，无解，只能二选一。
2. **数码管 AP = PIN_51**（【题】P7 题目2 提到该脚"与舵机复用"）→ **本设计不用小数点，AP 悬空不驱动**。
3. **按键需要自行设计防抖动电路**（【板】P8 原文）→ `keypad_scan` 必须含消抖。

### 3.3 显示器件极性汇总（写死进 RTL 注释）

- 数码管：**共阴**，`seg` 高有效、`cat` 低有效（选中的那一位）。
- 点阵：行**低有效**；列**高有效**，红绿两列**互斥**（同时为高/低都不亮，需显式给另一色低）。
- LD：高有效（本设计不用）。
- BTN：**按下为高**；SW：**往上为高**。

**扫描率（2026-10-09 校正，ERR-027 + ERR-038）**：**点阵与数码管的扫描都是 125 Hz**
（八行/八位各 1 ms，走 `tick_1k`），**占空比 1/8、亮度不变**；键盘扫描仍是 **200 Hz**
（消抖 `DEBOUNCE_MAX+1 = 4` 轮，⚠️ 一轮 = **2 个 tick_200 = 10 ms**，所以是 **40 ms**；
旧文档写"16 轮 = 80 ms"把 2 倍算漏了，真实值曾是 **160 ms** —— 见 `docs/06` **ERR-031**）。
⚠️ 旧实现两边都走 `tick_200` → 只有 **25 Hz**，
低于 LED 的临界闪烁融合（~60 Hz），上板肉眼可见闪。详见 `docs/02` §4.4/§7.1 与 `docs/06` **ERR-027**。

**闪烁节拍（2026-10-09 校正，ERR-038）**：B1 要求自检"以 **2 Hz** 闪烁"，但"每个
`tick_2hz`（500 ms）翻转一次"得到的是 **1 Hz** 方波 —— 审计时发现并要求/文档四处都按
2 Hz 记账。现在 `clk_gen` 另出 **`tick_4hz`（250 ms）**，`game_fsm` 在它上面翻转
→ **真正 2 Hz、50% 占空**；`tick_2hz` 只留给音效节奏。结算画面"先闪 2 个 2 Hz 周期
（= 4 × 250 ms = **1 s**）再常亮"也改成数 `tick_4hz`，与文档一致。

### 4.1 ⭐ S1「多种图案随机选择」的范围决策与实现（2026-10-09）

**为什么要限定在第二关**：B4 原文是"按【开始】键启动：点阵显示**完整拼图图案（图 4-1）**5 秒"
—— **第一关的图案被明文钉在图 4-1 上**（本工程已逐像素解码：4 行×3 列实心矩形）。而 B10 说
第二关"图案**自拟**"。所以：**把图案库加在自拟的第二关**，既实现了 A2 的"多种图案随机选择"，
又不动基本要求 B4 一个字。若老师另有口径（要求第一关也随机），只需在 `puzzle_pkg.vhd` 里给
第一关也加一组 `L1_PATS` 并让 `pattern_rom` 按 `i_pat` 选即可 —— 接口已经预留好了（`i_pat`）。

**硬约束（不满足就是死局）**：每幅候选图案必须能被**现成的零片集合恰好铺满**，而且零片
**只能平移、不能旋转**（A4 明确不做）—— 所以"恰好铺满"必须逐幅**穷举**验证。
`scripts/check_geometry.py` 与 `scripts/check_plans.py` **各自独立**枚举四块零片在 8×8 内的所有
平移摆位，要求存在恰好覆盖的解（不信任设计时的手算，也不允许用"旋转后能铺"这种过宽的证明）。

**4 幅图案**（`L2_PAT0` = 原第二关图案，**一字未改** → ERR-021/023 的整机证据继续有效）：

| # | 名称 | 8×8 样子（行 2~5） | 只许平移的精确铺法数 |
|---|---|---|---|
| 0 | 田（4×4 实心方块，列 2~5） | `..####..` ×4 行 | **1**（唯一） |
| 1 | 十（胖十字，列 1~5） | `..###...` / `.#####..` ×2 / `..###...` | **1**（唯一） |
| 2 | S/Z（锯齿，列 1~6） | `.####...` / `...####.` ×2 / `.####...` | **1**（唯一） |
| 3 | 阶梯（列 1~5） | `.####...` / `.#####..` / `..####..` / `...###..` | **2** |

玩家只要"把方块拖进轮廓"就赢，本质是**搬运**；换成异形后图案 0/1/2 **只有唯一一种**摆法，
玩家必须真的**拼出**轮廓（40 秒够用：散落最大位移 14 步、平均约 9 步/块）。
图案 3 恰好有**两种**铺法，正好留给 `tb_puzzle_ctrl` ⑭ 当 **ERR-021 的天然回归用例**：
故意摆第二种铺法（画面逐格一致、锚点元组与第一种不同）→ `o_solved` 必须为 1。

**选取点**：每次**进入 `S_PREVIEW` 的那一拍**（按【开始】开局 / 过关进入下一关）锁存 `rng_lfsr`
低 2 位 → `pat_sel`。预览 5 秒期间 `pat_sel` 稳定；散落用的是**同一个 LFSR 的后续值**，
两者互不干扰；上一局的散落已把 LFSR 推进若干步（步数还随拒绝采样变化），所以**重开一局图案会变**。

**判据红利**：ERR-021 之后成功判据是"**零片并集 == 目标图案**"（逐格比画面），换图案、换零片形状
**自动成立** —— 判据代码一行都不用改；只在 `puzzle_ctrl` 的"干净帧"快照里多跟踪一个 `pat_frm`（2 位），

离线重放：零次被拒、并集 == 图案）、`tb_pattern_rom` r05 = 8/8、`tb_piece_rom` r07 = 10/10
（含"四块形状互不相同且 == 设计意图 Q0/Q1/Q2/Q3"）、`tb_puzzle_ctrl` r15 = 18/18（含 ⑭ 等价摆法、
⑰ 图案切换作废）、`tb_puzzle_top` 模式 A/B（第二关预览显示被选中的那一幅 + **端到端拼通**
出绿对勾 + `PASS`）。

### 4.2 ⭐ 第二关零片为什么可以用"其他形状"（2026-10-09 第 11 工作阶段）

**起因（用户上板后的提问）**：图案库为什么只能用 2×2 的零片？——题目 B10 原文只要求
"四块零片、**零片图案自拟**、位置随机、不能重叠"，**零片形状完全自拟**；而工程引擎
`rtl/puzzle_ctrl.vhd` 本来就是按"任意形状"设计的（端口 `i_sh0..3` 是 64 位形状掩码 +
`i_h0..3`/`i_w0..3` 包围盒，第一关早已用了 1×3 横条 / 6 格阶梯 / L 形三格）。
所以"只能用 2×2"**不是技术限制，是当时自缚手脚**。

**改法**：第二关零片换成**四种异形**（3+2+5+6 = 16 格），图案库随之换成四幅用这四块
恰好铺满的轮廓（田 / 十 / S·Z / 阶梯）：

```
Q0 1x3 横条 3 格      Q1 1x2 竖条 2 格      Q2 J 形 5 格       Q3 六格块 6 格
###                    #                      ###                #..
                       #                      ..#                ###
                                              ..#                .##
```

⚠️ 零片与图案仍然全是**编译期常量**：`piece_rom` 仍 **0 LE**、`pattern_rom` 仍 **4 LE** ——
换成异形**一个 LE 都没多花**（"装不下"的从来不是这里）。

**代价与取舍（如实记录，见 `docs/06` ERR-032）**：形状尺寸不再统一（原来四块都是 2×2，于是散落里
`x mod ch` 的除数 `ch`/`cw` 被综合器当**常量**折叠掉了）；异形让除数真的随零片变化（5/6/7）→
**实例化出两个变除数除法器**，实测整机 Fmax **44.77 → 36.68 MHz**（最差 slack −7.3 ns、
TNS −926 ns）。修法：`x ≤ 7`、`ch ≥ 4` 时 `x mod ch` 等价于**一次条件相减**，
实测 Fmax 回到 **50.06 MHz（TNS 0）**、面积 1246 → **1254 LE（+8）**。
