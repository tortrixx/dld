## 1. 模块职责与在系统中的定位

<div class="plain-explain-box">
  💡 <strong>大白话一句话理解本模块</strong>：<br>
  它是 8×8 双色点阵屏的<strong>“物理底层刷屏驱动与色彩发生器”</strong>。屏幕上的 64 个双色小灯由它以 1 kHz 的节拍从上往下逐行点亮（每秒刷屏 125 次，绝无水波纹和频闪）。它直接控制 8 根行线与红、绿两组列线：单通红列显红（底图/红叉）、单通绿列显绿（活动块/绿勾/告急幽灵）、红绿并联全通电就会利用光学混色呈现出亮黄色（已锁定拼图块）！
</div>

`dot_matrix_scan` 模块是整个拼图游戏界面的**物理光电输出终端**。它直接与实验箱上的 8×8 双色（红/绿）LED 点阵屏物理引脚对接，负责将逻辑层计算出的二维画面映射为真实的物理发光。

核心职责包括：
1. **8 行低电平单相选通驱动**：以 1 kHz 节拍驱动 8 行物理共阳极/共阴极引脚进行独热轮巡；
2. **红绿双通道独立直通控制**：同时接收当前行的 8 位红色列数据与 8 位绿色列数据，高电平点亮对应像素；
3. **双色混合机制（红+绿=黄）**：通过两组独立列引脚的电平叠加，合成出红色、绿色与黄色三种游戏视觉基色；
4. **同拍寄存防串光**：行选通与双色列数据同拍同步更新，杜绝跨行错行与虚影。

## 3. 代码核心原理与微架构实现

### 3.1 物理引脚行编号与逻辑行的“镜像修正”

在实验箱硬件手册中，行引脚定义为 `ROW0..ROW7` 对应 `PIN_8..PIN_1`，但手册从未标明 `ROW0` 究竟是屏幕的物理顶部还是底部！
* 在上板调试（`board_test_top`）时，我们在逻辑第 0 行画了一个红点，结果红点却出现在了点阵屏的**最底部**！
* **实测裁决**：物理上的 `ROW0` 实际是屏幕的最底行，而逻辑行 0 是玩家眼中的屏幕最顶行；
* **RTL 内部反相译码**：代码在 `with i_row select` 内部直接修正了这一镜像关系：
  ```vhdl
  with i_row select
      row_sel <= "01111111" when "000",   -- 逻辑行 0 (顶部) -> 驱动 ROW7 (PIN_1)
                 "10111111" when "001",
                 ...
                 "11111110" when others;  -- 逻辑行 7 (底部) -> 驱动 ROW0 (PIN_8)
  ```
  这保证了软件工程中的坐标 $(0,0)$ 与物理点阵屏的左上角绝对一致，且无需篡改物理约束 `.qsf` 引脚文件。

### 3.2 严禁驱动板载 LD8..LD15 的硬件冲突约束

在硬件板卡电路原理图中，存在一个极隐蔽的硬件引脚复用陷阱：
* 板上的 `PIN_38..PIN_45` 同时并联了 **点阵绿色列 COLG0..COLG7** 与 **独立发光二极管 LD8..LD15**；
* 如果在工程中试图点亮或驱动 LD8..LD15，就会强制拉低或拉高绿色列电平，导致**双色点阵彻底丧失绿色发光能力**（直接破坏要求 B6“选中的零片与未选中的显示不同颜色”）；
* **工程裁决**：在顶层引脚约束中，全工程**坚决不分配、不驱动 LD8..LD15 相关的任何引脚**，将其完全留给双色点阵专用。

  - 点阵行推进与数码管完全共享 1 kHz 节拍，8 行扫描周期为 8 ms，整屏刷新率同样为超临界 **125 Hz**，占空比严格为 1/8。不仅亮度适中均匀，而且无论使用手机高速摄像头拍摄还是肉眼直视，均无任何水波纹或闪烁。

## 6. 🎓 老师答辩必问与标准回答（核心快问快答）

<div class="defense-box">
  <div class="defense-title">💡 老师随机抽查：双色点阵驱动核心答辩点</div>

  <div class="defense-q">Q1：双色点阵屏是怎么显示出三种颜色的？它的硬件极性是什么？</div>
  <div class="defense-a">
    <strong>标准回答：</strong><br>
    老师，双色点阵屏的每个像素点内部实际上封装了一个红光 LED 和一个绿光 LED，二者共用行电极：<br>
    1. <strong>极性</strong>：行（ROW）为<strong>低电平选通</strong>，红色列（COLR）与绿色列（COLG）为<strong>高电平点亮</strong>；<br>
    2. <strong>色彩合成</strong>：<br>
       - 当行低、红列高、绿列低时，只有红光管导通，显示<strong>纯红色</strong>（用于目标底图、失败叉和游离零片）；<br>
       - 当行低、红列低、绿列高时，只有绿光管导通，显示<strong>纯绿色</strong>（用于当前操作的活动零片、胜利对勾和告急幽灵）；<br>
       - 当行低、红绿两列同时拉高时，红绿两管同时点亮，根据加色混色原理，肉眼看到的是<strong>明亮的黄色</strong>（用于已确认锁定的零片和自检全屏点）。
  </div>

  <div class="defense-q">Q2：你们是怎么防止点阵屏在扫描时错行或者出现鬼影的？</div>
  <div class="defense-a">
    <strong>标准回答：</strong><br>
    点阵产生错行鬼影的根因是“行号改变了，但列数据还滞留在上一行的状态”。<br>
    在我们的 <code>dot_matrix_scan</code> 中，行选通信号 <code>o_row</code>、红色列 <code>o_colr</code> 和绿色列 <code>o_colg</code> 是由<strong>同一个 process 并在同一个 50 MHz 主时钟上升沿同步寄存输出</strong>的。<br>
    当行号步进时，对应的行选通与新一行的列像素数据在同一纳秒内瞬间同步切换，行引脚和列引脚之间完全零时差，因此绝不会出现第 2 行被第 1 行的数据点亮的鬼影现象。
  </div>

  <div class="defense-q">Q3：为什么你们的代码里行译码看起来是反过来的？</div>
  <div class="defense-a">
    <strong>标准回答：</strong><br>
    这是我们在硬件实物上用测试固件抓出来的<strong>引脚物理映射细节</strong>。<br>
    实验板手册把引脚标为 ROW0～ROW7 对应 PIN_8～PIN_1，但在物理布线上，物理 ROW0 实际上位于点阵屏的最下方，而逻辑上的第 0 行是游戏画面的顶部。<br>
    为了让 VHDL 逻辑内部保持标准的“从上到下 0..7”直观坐标系，我们在 <code>dot_matrix_scan</code> 的译码器中将逻辑行 0 映射给物理 ROW7（PIN_1），逻辑行 7 映射给物理 ROW0（PIN_8）。这样既对齐了物理真实世界，又保持了内部算法的优雅简洁。
  </div>
</div>
