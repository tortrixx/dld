### 1.2 本次修掉的缺陷（**全部先经代码核实，非猜测**）

按"最贵"排序，全部可作报告评分项⑤的素材。

#### ERR-001 · `btn`（复位键）引脚漏配 —— 静默落错脚

| 项 | 内容 |
|---|---|
| **现象** | 编译通过，但 Fitter 报 `No exact pin location assignment(s) for 1 pins of 52` |
| **定位** | `puzzle.fit.summary` 显示 52 引脚，而 `.qsf` 只写了 51 条 → 查 `output_files/puzzle.pin`，发现 `btn` 落在 `PIN_50`（非 61） |
| **根因** | 生成器只为 `TOP_PORTS` 里**列出**的端口写约束。**未被约束的输入端口不会报错**，Quartus 把它随机放到空闲脚 |
| **修法** | 补 `btn`；并加守卫：端口若在引脚表查不到就报错退出 |
| **教训** | **"编译成功"≠"引脚接对了"。** 必须把 `.pin` 与手册逐条比对，并检查 `No exact pin location assignment(s)` 的数字是否为 0 |

#### ERR-002 · 键盘诊断固件漏配键盘引脚 —— **本次最长的一次误判**

| 项 | 内容 |
|---|---|
| **现象** | "按任何键都没反应"，且多版诊断固件读数荒谬（行线 `1 0 1 0`、全列拉低也不动） |
| **误判过程** | 先后怀疑：键盘极性、硬件损坏、排线松动、按键电路故障。实测甚至"证明"全列拉低时按键也不起作用 |
| **真因** | 新加的 `keypad_diag_top` / `keypad_raw_top` 在生成器的 `TOP_PORTS` 里**只列了时钟/数码管/点阵端口，漏了 `kp_row`/`kp_col`**。生成器只给列出的端口写约束 → **键盘引脚完全没被约束**，被 Quartus 放到 `49/102/130/88/85/127/48/20` 等无关引脚上。固件跑得完全正常，只是驱动/读取的是**别的引脚** |
| **定位手法** | 写 `scripts/check_keypad_pins.py`，把"手册、生成器、fitter 实际落点"三方逐条对比 → 8 个键盘信号全部 MISMATCH，立刻定位 |
| **修法** | ① 补全两个诊断顶层的端口清单；② 给生成器加**第二道守卫**：解析顶层 VHDL 的 entity 端口列表，**任何未列入 `TOP_PORTS` 的端口都直接报错退出** |
| **教训** | **"没配引脚"是最危险的一类错误：它不报错、能编译、能运行，现象与"硬件坏了"完全一样。** 判据必须是 `.pin` 实测落点，不是"应该配对了"。 |
| **补充教训** | 第一道守卫（"列出的端口必须有引脚"）**抓不到"漏列端口"** —— 守卫本身也要被审查。第二道守卫用 entity 端口列表反向校验，并做了负向测试（去掉 `kp_col` 后确实报错） |

#### ERR-003 · 键盘轮次结果被提前清零（**主因**）

| 项 | 内容 |
|---|---|
| **现象** | 键盘引脚修正后仍按键无反应 |
| **根因** | `round_code` 在 `ST_IDLE` 状态**每个时钟**都被清成 `K_NONE`，而该状态持续约 **250 000 个时钟**；消抖级只在 **200 Hz tick** 采样一次。于是采样时永远读到 `K_NONE` → `o_key` 恒为 0 → 永不产生"按下"脉冲 |
| **附带缺陷** | 只捕获了 `phase=3`（第 3 列），**第 0~2 列的按键永远读不到** |
| **修法** | 改为"取本轮**任意已稳定相位**的第一次命中"，并**保持到下一轮开始**；消抖级直接读保持寄存器（避免同沿读到旧值滞后一轮） |

#### ERR-004 · 键码编码与比较表不一致

| 项 | 内容 |
|---|---|
| **根因** | 扫描器发的是 `4*列+行`（列优先），而 `puzzle_pkg` 的 `K_*` 常量按 `K_START="0001"` 布局。两者**没有一个键能对上**，所以即使扫描正常，游戏也永远不会响应"开始" |
| **修法** | 扫描器统一输出**行优先键号 `4*行+列`**（键盘的自然读序）；`game_fsm` 用**唯一一张显式映射表** `key_of()` 把它译成游戏按键。物理布局只描述在一个地方，一次测量即可修正 |

#### ERR-005 · 拼图限时从未加载

| 项 | 内容 |
|---|---|
| **根因** | `S_PREVIEW` 结束时只写 `st <= S_PLAYING`，**没有给 `cnt` 装初值**；`T_LEVEL1`/`T_LEVEL2` 在代码里**从未被引用**。`cnt` 还停留在预览的 1，于是下一个 1 Hz tick 立刻走 `cnt <= 1` 分支 → **进关不到 1 秒就判失败** |
| **修法** | 进关时按关卡装 `T_LEVEL1`(30 s) / `T_LEVEL2`(40 s) |

#### ERR-006 · `o_go` 握手无"完成"记忆 → 无限重复散落

| 项 | 内容 |
|---|---|
| **根因** | 散落请求/应答握手没有记住"已请求过"。引擎一回到 `SH_IDLE`，`i_shuf_busy` 落下，握手**立刻再次请求** → 引擎几乎一直在重新散落。后果：每次请求都会清掉 `sel`/`locked`（"确认"永远存不住），且引擎忙时忽略按键 |
| **修法** | 加 `go_done`：每局只请求一次，离开 `S_PLAYING` 时重新武装 |

#### ERR-007 · 选中零片**永远显示不出绿色**（要求 B6 未达成）

| 项 | 内容 |
|---|---|
| **根因** | 渲染时 `redrow := cov or (tgtrow and (not cov))`，其中 `cov` 是**所有**零片格；而绿通道只由 `cov` 内的格子构成 → **绿色恒为红色的子集**，纯绿格不存在。选中零片实际显示为**红+绿=黄**，与"已锁定"完全一样 |
| **修法** | 单独累加"选中行" `selrow`，并从红通道里**排除**它：`red = (cov and not selrow) or ghost`，`green = locked or selrow` |

#### ERR-008 · 第二关目标图案比零片位置低一行

| 项 | 内容 |
|---|---|
| **根因** | `L2_TARGET_MASK` 的 4×4 方块在**第 3~6 行**，而四块零片的目标锚点在**第 2~5 行**。红色底图（虚影）画在**实际拼合位置下方一行** → 玩家照着底图拼**永远拼不对** |
| **修法** | 修正常量；并在 `scripts/check_geometry.py` 里加**永久校验**："目标图案必须等于各零片在目标锚点上的并集"（L1/L2 都查） |

#### ERR-009 · 待机/预览的点阵内容错误

| 项 | 内容 |
|---|---|
| **根因** | 顶层状态多路器只特判了 `SELF_TEST`/`S_WIN`/`S_FAIL`，**其余状态全部显示引擎画面**。但散落只在 `S_PLAYING` 才开始，所以待机/预览时零片仍全部堆在锚点 (0,0) → 点阵左上角出现一坨。而要求 B2 是"点阵全灭"、B4 是"显示完整图案" |
| **修法** | `S_IDLE` 点阵全灭；`S_PREVIEW` 直接切目标图案常量（不经过引擎） |

#### ERR-010 · 胜负图案上下镜像

| 项 | 内容 |
|---|---|
| **根因** | 本工程掩码约定是 `bit = 8*行+列`（第 0 行在 bit 7..0），但取 `WIN_MASK`/`FAIL_MASK` 的一行时按 `63..56` 当第 0 行 → 两个结束画面**上下颠倒**。`FAIL_MASK` 恰好上下对称所以看不出来，`WIN_MASK`（对勾）看得出来 |
| **修法** | 按正确方向取行 |

#### ERR-011 · 2 Hz 闪烁信号是单时钟脉冲（"自检什么都不显示"）

| 项 | 内容 |
|---|---|
| **现象** | 现场："拨上 SW7 后 2 秒内点阵和数码管都是灭的，只有蜂鸣声" |
| **根因** | `clk_gen` 的 `tick_2hz` 是**单时钟脉冲**（每 500 ms 宽 10 ms）。直接把它当"闪烁电平"用 = **每 500 ms 只亮一个时钟** → 肉眼几乎不可见 |
| **修法** | 改为**对 tick 翻转的 50% 占空方波**（这才是要求 B1 说的"以 2Hz 频率闪烁"） |

#### ERR-012 · 点阵刷新率只有 ~3 Hz（明显闪烁）+ 显示与渲染不同源

| 项 | 内容 |
|---|---|
| **现象** | 现场："自检时还是有点闪烁"、"点阵中的点频率有点慢，有明显的闪烁感" |
| **根因①** | 渲染相位计数器 `ph` 是 **3 位（0~7）**，但 case 只用了 **0~4**；相位 5/6/7 落进 `others` 分支**又发布了一次行** → 每行实际用 8 拍而非 5 拍，帧率降到 200/(8×8) ≈ **3 Hz** |
| **根因②** | 引擎按 `tick_200` 推进行，而点阵按 `t_40` 扫描，**两个计数器不同源**，"正在显示的行"与"正在渲染的行"长期不一致 → 撕裂/闪烁 |
| **修法** | ① 相位改为 mod-5；② 渲染改为**每拍累加一整行到 64 位帧寄存器**（8 拍一帧 → **25 Hz**），矩阵在同一 `tick_200` 上按行扫描 |

#### ERR-013 · 预览后矩形底图不消失，挡住零片

| 项 | 内容 |
|---|---|
| **现象** | 现场："出现零片，但是开始的矩形方阵没有消失！" |
| **判断** | 这不是缺陷而是**设计取舍错了**：预览已经显示过完整图案（B4），游戏态再画一层红色底图（虚影）既非要求，又**把零片盖住了** |
| **修法** | 游戏态把引擎的 `i_target` 置零 → 拼图区只剩零片（引擎的虚影逻辑保留，供自检与诊断使用） |

### 1.3 面积优化的实测记录（**报告"资源利用"与"故障分析"都可引用**）

`puzzle_ctrl` 从**无法放进器件**做到 **563 LE**，共 7 个版本，每一步都有 map 报告实测值：

| 版本 | 做法 | 实测 LE | 结论 |
|---|---|---|---|
| v1 | 每块零片用 64 位**变距移位** | **4690** | 64×6 交叉开关，超器件 3.7 倍 |
| v2 | 同上，改"逐行 CASE"辅助函数 | **2969** | 仍太大 |
| v3 | 循环里**变址读数组** | **2995** | 变址读变成多路器，且**每个使用点各复制一份** |
| v4 | 固定移位维护 64 位占位寄存器 | **2350** | 寄存器 504 个，LUT-only 1717 |
| v5 | 改**行扫描渲染**（8 位累加器） | **3751** | 寄存器降到 115，但未展开的重叠判定实例化 32 个 `row_mask` |
| **v6** | **重叠判定也串行化：每拍比一行** | **994** | 任一时刻只有一个 `row_mask` 存活 → 可共享 |
| v7 | 关键路径流水（寄存器化状态/音效/移动请求、除法器换查找表、`srl8` 改 mux 树） | **563** | 最终值 |

**核心结论**：面积不是被"某一条语句"吃掉的，而是被
**"宽向量 + 变址访问 + 未展开调用"三者的复制效应**吃掉的。
判断依据只能来自 map 报告的**层次面积表**与 TimeQuest 的**路径报告**，不能靠估计。

### 1.4 ⚠️ 关键路径（诚实记录）

| 项 | 值 |
|---|---|
| `.sdc` 约束 | 50 MHz（周期 20 ns） |
| **实测 Fmax** | **41.1 ~ 41.5 MHz**（周期 ≈ 24.1 ns） |
| 是否满足约束 | ❌ **未满足** |
| 功能风险 | **低**：本设计所有外设都是人机接口（按键、点阵、数码管、蜂鸣器），
实际工作频率需求 < 1 kHz，41 MHz 有 4 万倍余量 |

**已做的流水化**（把关键路径从 26 ns 降到 24 ns）：
① 除法器换查找表；② `o_solved`/音效码寄存器化；③ 移动请求两拍流水；④ 行号寄存器化；⑤ `srl8` 由逐位循环改 7 路 mux 树。

**待办**：继续流水化，或把约束改为 40 MHz 并如实说明。
**不得**为了"看起来满足"而直接改约束而不说明。

# 第 2 阶段：仿真驱动的缺陷发现（ERR-016 ~ ERR-019）

> 背景：逐模块 + 整机功能仿真跑起来之后（`docs/03`，12 个模块/场景、117 条断言），
> 一共抓出 4 个**板级现象看不出来**的真缺陷。这一节按 ERR-001~013 的同样格式记录：
> 现象 / 定位过程 / 根因 / 修法 / 复验 / 教训。

## ERR-016 · 重叠检查的行号流水没对齐

**现象（仿真）**
`tb_puzzle_ctrl` 断言 ②（随机散落后三块零片必须两两不重叠）失败：实测 P2@(4,1) 与
P1@(3,1) 在格子 (4,2)、(5,1) **重叠**。断言 ⑤（横条右移撞上楼梯形应被拒）也失败。

**定位过程**
1. 先把 `chk_row` / `chk_orow` / `chk_prow` 声明进 `.vwf`（BURIED），逐拍打印比对过程；
2. 发现同一拍里"候选零片的行索引"与"邻居零片被比对的板面行"**相差 1**；
3. 于是一条不变量就够判定了：
   `chk_orow == (chk_prow - 候选锚点行) mod 16` —— 修好前必然不成立。

**根因**
`chk_orow` 是**流水寄存器**（为了缩短关键路径而加的一级），但比较邻居时用的是
**当前** `chk_row`：等于拿候选的第 r 行去比别人第 r+1 行。既漏判真重叠，又把合法落位
误拒（实测：本该落在 (0,0) 的第 1 块被误拒 → 走了确定性回退）。
另外循环条件 `chk_row = 8` 使实际**被评估的板面行只有 -1..6，第 7 行从来没查过**。

**修法**
* 新增 `chk_prow` 寄存器：与 `chk_orow` **同一拍对应的板面行**；
* 邻居比较统一改用 `srow := chk_prow - prow`；
* 循环条件由 8 改为 9（评估行变成 -1..7，第 7 行进入覆盖）；
* 检查启动时把 `chk_orow`/`chk_prow` 置 `"1111"`，让第一拍空转，避免用到上一轮的残留值。

**复验**
断言 ②⑤⑫ 全部通过；断言 ⑫ 实测 **330 个比对拍**全部满足不变量。

**教训**
**流水线的"延时"必须一路跟到底**：寄存了一路数据、却拿另一路的当前值去比，
等价于把整个比对错开一行 —— 而且它既不报错、也不影响"看起来能不能跑"。

## ERR-017 · 散落时"跳过自己"用错变量

**现象（仿真）**
把散落的随机源固定（`rnd_val` 恒 0）做确定性实验时，第 3 块零片**正好落在第 1 块身上**：
`o_pos` 实测 P0=(0,0)、P2=(0,0)。

**定位过程**
1. 让随机源恒定 → 候选锚点唯一 → 位置可复现；
2. 逐块观察 `o_pos` 的提交顺序，发现第 3 块的候选**没有被第 1 块挡住**。

**根因**
"跳过自己"的掩码写成了 `sel`：

```vhdl
if (sel /= "00") and (sh_k /= "00" or chk_kind = '0') then  -- 散落时 sel 恒为 0
```

而散落期间 `i_go` 会把 `sel` 清成 0，正在摆放的那一块是 **`sh_k`**。后果有两个：
候选**永远不和第 0 块比**（两块可以叠在同一格），同时会拿候选和**它自己散落前的位置**
比（合法的散落被误拒）。

**修法**
按检查类型选"我自己是谁"：

```vhdl
if (chk_kind = '0') then me := std_logic_vector(sel);    -- 移动：被移动的那块
else                     me := std_logic_vector(sh_k); end if;   -- 散落：正在摆的那块
```

四处比较统一用 `me`。

**复验**
断言 ②（随机散落不重叠）通过；确定性散落的三块落位变成
P0=(4,1)、P1=(0,4)、P2=(4,0)，只与"硬编码回退锚点"冲突（即 ERR-018b）。

**教训**
**"跳过自己"的索引必须与"当前正在处理的对象"同源**。一旦这两个概念用了不同的变量，
缺陷会同时以"漏判"和"误判"两种相反的形式出现 —— 只调试一种现象会越调越乱。

## ERR-018 · 散落重试不再抽新候选（a）＋ 回退锚点不查重叠（b）

**现象（仿真）**
波形里 `chk_pos`（候选锚点）在一次散落的 **16 次"尝试"中完全相同**；
最终零片落到硬编码回退锚点，而回退锚点与别的零片的随机落位**重叠**。

**定位过程**
1. 把 `chk_pos`/`chk_row`/`rnd_val` 一起放进波形，逐次尝试打印；
2. 看到 `rnd_val` 每次都变、而 `chk_pos` 一动不动 → 说明**候选根本没有重新抽取**；
3. 回读 `CH_DONE` 的失败分支：只做了 `sh_att + 1`，`sh` 仍停在 `SH_CHK`，
   而候选只在 `SH_TRY` 里更新 —— 重试从不回 `SH_TRY`。

**根因（a）**
所谓"16 次拒绝采样"其实是**把同一个位置查了 16 遍**。于是只要首候选冲突，
就必然 16 次全败 → 落到硬编码回退锚点。**B5 的"位置随机"实际上被压缩成了"首抽落点"。**

**根因（b）**
回退锚点 `(0,0)/(0,4)/(4,0)/(4,4)` 是写死的，且**不再做重叠检查**。
这三个锚点彼此不冲突，但**回退锚点与别的零片的随机落位**可能冲突。

**修法（a）**
失败重试加一句 `sh <= SH_TRY;` —— 回到候选生成状态、重新抽一个位置。

**处置（b）：如实记录、本轮未修**
(a) 修好后，回退只在"随机源连续 16 次都给出冲突候选"时才可能触发；真实设计里
`rnd_val` 来自 LFSR、每次尝试都会翻新，触发概率约 **1e-7** 量级。
本轮**不为这个角例再改硬件**（器件已到 95% 面积），但把它写进报告"已知不足"，
并让 `tb_puzzle_ctrl` 的断言 ⑯ 用 `rnd_val` 恒 12 的极端激励**复现并留档**。

**复验**
断言 ③（确定性散落落到三个回退锚点）与 ⑯（复现 ERR-018b）都按预期通过。

**教训**
**"重试"必须真的改变输入**。一个不改变任何输入的循环，只是把"一次失败"变成
"一次失败 + 15 次空转"，并且会把失败**推到一条没有保护的兜底路径**上去。

## ERR-019 · `srl8` 移位方向反了（本条另外见 `AI_LOG.md` 的"AI 结论被人工驳回"记录）

**现象（仿真）**
`tb_puzzle_ctrl` 断言 ⑧（着色逐格与独立几何模型比对）失败：**选中的零片一格都没画出来**
（实测红0绿0，模型期望红0绿1）。

**定位过程**
1. 断言 ⑧ 是把 64 个格子逐格算出来的，所以"整块零片消失"这种结论不需要人工看图；
2. 顺着渲染链回读：`row_mask(shp, sr, ac)` → `srl8(base, ac)`；
3. 用 4 位例子手算：`v := '0' & r(3 downto 1)` → 位号 3 的格子跑到位号 2 =
   **在面板上向左移了一列**；而"把零片放在锚点列 ac"要求 `v(j) = r(j-ac)`，即**向右移**。

**根因**
`srl8` 的 8 个分支全部把数据往**位号小**的方向搬：

```vhdl
when 1 => v := '0' & r(7 downto 1);   -- v(c) = r(c+1)：位号变小 = 面板上向左
```

后果：**锚点列 > 0 的零片全部画错列，并从左边界丢格子**（1x3 横条在锚点列 2 时
只会画出一个点）。同一条函数还供**重叠判定**使用，所以碰撞检测也一并错了。

**为什么上板看不出来**
预览画面（B4 要求"完整图案"）是**直接取图案常量**画的（`puzzle_top` 里 `prev_row`），
**根本不经过这个移位**；散落时"有零片出现"也确实能看到 —— 只有"零片画在哪几列、
有没有丢格子"错了，而这一点在板子上要靠数格子才能发现。

**修法**
改成往位号大的方向搬（即 `v := r(6 downto 0) & '0'` 等）。
⚠️ 注意：直接写"右移"会让综合器**没法再做常量折叠**（旧的错误左移会把低列格子推出
边界，锚点列 ≥3 的整片逻辑被剪掉）→ **面积从 958 LE 涨到 1201 LE（95%）**，
Fmax 从 42.24 MHz 降到 **41.39 MHz**。中间试过"位序反转 + 左移 + 再反转"的等价写法，
实测**同样 1201 LE**（等价函数在综合后就是同一张网表），说明这个代价是**方向正确
本身带来的**，不是写法问题。

**复验**
断言 ⑧ 全部 64 格与独立模型一致；选中的零片 6 格**全部"红0绿1"（纯绿）**，
锁定的零片 3 格"红1绿1"（黄）—— 即 B6/B8 的着色语义逐格成立。

**教训**
1. 🚨 **这一条此前被"人工核实"过并被明确驳回**（见 `AI_LOG.md` §2.5：当时的推理是
   "`v := '0' & r(7 downto 1)` 即 `v(c)=r(c-1)`，方向是对的"）。**这一步推理本身就是错的。**
   **人工验算也会错；最终判据必须是可执行的行为比对（仿真/实测），而不是"再想一遍"。**
2. **"面积小"有时是 bug 的副产品**：一个错误的移位方向让综合器剪掉了一大片网络，
   于是"面积看起来很美"。修 bug 之后面积反弹，**不能反过来当成"修坏了"** ——
   要么接受（本项目：95%，仍能放下），要么另找真正的算法优化。
3. **显示类缺陷的第一判据是"逐格比对"**：`docs/02` 里"每行 0x1C"这种断言，
   比"看着有没有亮"强太多。

# 第 3 阶段：上板验收暴露的问题（ERR-020）

> 背景：按 §4.1 重新烧录整机固件后，现场逐步验收（自检→待机→预览→散落→选择）——
> **B1/B2/B4/B5/B6 全部正常**，但**方向键按下去零片完全不动**。

## ERR-020 · 方向键失效：方向比移动请求晚一拍锁存

**现象（现场）**
【开始】能启动、【选择】能切换绿色零片，但**四个方向键按下去零片一动不动**（也没有
"被拒绝"的表现，就是不响应）。

**定位过程（先分成两半：是"键没传进去"还是"引擎没用上"）**
1. 键位映射是嫌疑之一，但那时映射还是"推测值"，无法区分。
2. 更关键的是：`game_fsm` 的判决与引擎的接口是**内部信号**，可以直接看波形 ——
   于是在 `tb_puzzle_top` 里加了一条**与键位映射无关的协议判据**：
   > 只要 `game_fsm` 发出了方向脉冲（`up_r/down_r/left_r/right_r` 任一为 1），
   > 引擎就必须在**同拍或其后两拍内**锁进非 0 的 `mv_dir`。
3. 仿真实测：**方向脉冲确实发了 3 次**（说明键盘与状态机都没问题），
   而 `u_puzzle|mv_dir` **全程没有任何跳变、恒为 0** → 问题在引擎侧。

**根因**
`game_fsm` 的 `o_up/o_down/o_left/o_right` 与 `o_move` 是**同拍、各一个时钟**的脉冲；
而 `puzzle_ctrl` 把方向锁存放在了"移动请求流水"的**第二级**：

```vhdl
elsif (i_move = '1') then mv <= '1'; end if;          -- 第 T 拍：只记下"有请求"
...
if (mv = '1') and (chk = CH_IDLE) then                -- 第 T+1 拍才采方向
    mv_dir <= i_up & i_down & i_left & i_right;       -- 此时方向脉冲已经撤销 → "0000"
```

→ `mv_dir` 恒为 `"0000"`：夹紧不生效，候选锚点就是原锚点，重叠判定当然通过，
于是"移动"变成**原地重算**，零片纹丝不动。

**修法**
方向与移动请求**同一拍锁存**（一行搬位置），流水线只保留锚点的寄存（面积/时序收益不变）：

```vhdl
elsif (i_move = '1') then
    mv     <= '1';
    mv_dir <= i_up & i_down & i_left & i_right;        -- ★ 与请求同拍
end if;
```

**复验**
* 仿真：`tb_puzzle_top` 断言 ⑧（方向协议不变量）修复前 ❌、修复后 ✅；
  断言 ⑨ 同时确认候选锚点确实随方向改变（不再是原地重算）；整机 **9/9 通过**。
  修正后整机面积 1202 LE（+1 LE），Fmax 仍 41.39 MHz。

**教训**
1. **脉冲宽度是接口契约的一部分**。一个"1 拍脉冲"的握手，跨模块多流水一级就会
   丢信息。**凡是把脉冲寄存下来的那一级，必须把同一组脉冲一起寄存**。
2. **测试台的时间假设必须与现实一致**：`tb_puzzle_ctrl` 当时把方向电平**多保持了
   10 拍**，所以"方向能锁进去"，掩盖了缺陷；而 `tb_puzzle_top` 走的是**真实时序**
   （键盘→扫描器→状态机→引擎），一按就露馅。
   → **"深到底"的整机场景仿真不是锦上添花，它是唯一能覆盖跨模块时序假设的判据。**
3. 这条也是**先分层、再定位**的范例：先用一条"与键位映射无关"的协议判据把

## 键位布局重排（按板子手册**附图 26**，2026-10-08）

**为什么之前搞不清键位**
旧稿参考的是**课程题目 PDF 的键盘示意图**（那张图上印的是 `7 8 9 / 4 5 6 / 1 2 3 /
0 清屏 确认`），但**实际板子的 4×4 键盘上只有 KEY1~KEY16 的编号**，两者根本不是同一张图。
现场反馈"只有编号、没有功能印字"之后，改为**从板子手册**取证：

* `MAXII数字实验板（LCM12864液晶版）.pdf` **附图26**（4×4 键盘模块实物图）上印着：
  * 四列 **COL0~COL3**（从左到右）
  * 四行 **ROW3（最上）… ROW0（最下）**
  * 16 个键 **KEY1~KEY16**，按**从上到下、从左到右**编号
* 手册正文：`COL0~COL3 → 117/118/119/120`、`ROW0~ROW3 → 111/112/113/114`
* `.qsf` 与之一致：`kp_col[0..3]→117..120`、`kp_row[0..3]→111..114`
* 扫描器：`o_key = 4*行号 + 列号`，其中"行号"就是 `kp_row` 的下标 → **行0 = ROW0 = 最下一排**

于是物理键与键号的对照表（键号 = 4×行 + 列）为：

| 丝印行 \ 列 | COL0 | COL1 | COL2 | COL3 |
|---|---|---|---|---|
| **ROW3（最上）** | KEY1 = 12 | KEY2 = 13 | KEY3 = 14 | KEY4 = 15 |
| **ROW2** | KEY5 = 8 | KEY6 = 9 | KEY7 = 10 | KEY8 = 11 |
| **ROW1** | KEY9 = 4 | KEY10 = 5 | KEY11 = 6 | KEY12 = 7 |
| **ROW0（最下）** | KEY13 = **0（不可用）** | KEY14 = 1 | KEY15 = 2 | KEY16 = 3 |

> ⚠️ **键号 0 不可用**：扫描器用 `"0000"` 表示"没有按键"（`K_NONE`），所以 KEY13
> 与"什么都没按"**无法区分**，永远不能当控制键。旧映射表里的 `when "0000" => K_LEFT`
> 其实是**死代码**（仿真断言 ⑧ 里"键号 0 按下去没有任何事件"就是这条的证据）。

**新布局（把 7 个控制键收进右下 3×3 的一块，方向做标准十字）**

|  | COL1 | COL2 | COL3 |
|---|---|---|---|
| **ROW2** | KEY6 | **KEY7 = 上** | KEY8 |
| **ROW1** | **KEY10 = 左** | **KEY11 = 确认** | **KEY12 = 右** |
| **ROW0** | **KEY14 = 开始** | **KEY15 = 下** | **KEY16 = 选择** |

* 方向是标准的"十字"（中间是确认，和数字小键盘的 8/4/5/6/2 一个手感）；
* **开始 / 选择保持现场已经用熟的 KEY14 / KEY16**（两个实测锚点不动，避免重新学）；
* 键号全部非 0、互不重复；`key_of()` 仍是**全项目唯一的映射点**。
* 现场验收：自检→待机→预览→散落→选择→方向移动→确认锁定**全部正常**。

**教训**
**"图"必须确认是"哪台设备的图"**。旧稿把题目里那张通用键盘示意图当成了本板键盘，
于是键位一直对不上；真正的权威来源是**板子自己的手册附图**（上面有丝印）。

# 第 4 阶段：ERR-021（第二关拼对却判失败）

> 背景：按第 3 阶段的新键位重烧整机固件后，现场**第一关能过、第二关拼对后按"确认"仍然出"叉"**。
> 这一条的特别之处在于：**先有上板现象，再由仿真复现并钉死判据**（ERR-016~019 是反过来的
> ——先被仿真抓出来，然后才发现"上板看起来正常"）。

## ERR-021 · 成功判据选了"内部编号"，而不是"玩家看得见的画面"

**现象（上板原话）**
"第一关能过；第二关即使把四块拼成和预览一模一样的图案，按确认还是失败（出叉）。"

**根因**
`rtl/puzzle_ctrl.vhd` 原来的成功判据是"第 k 块的锚点 == 写死的 `L2_TGT[k]`"：

```vhdl
o_solved <= '1' when (locked = "1111") and (pos 的第 k 块锚点 = L2_TGTk) and ... ;
```

而第二关的四块零片是**完全相同**的 2×2 方块，填满 4×4 目标一共有 **4! = 24 种**摆法，
**画面逐格完全一样**；锚点判据只认其中 1 种 → 玩家拼对了也只会得到 **23/24 ≈ 96%** 的失败率。
第一关的 4×3 矩形同样有 **2 种**等价铺法（`.ref/solve_l1.py` 早就枚举出来了，
当时只当成"可解性通过"），锚点判据只认 1 种 → 命中率只有 **1/2**（之前"能过"有运气成分）。

**证据（数量级靠枚举，结论靠可执行的行为对照）**
1. **Python 枚举**（`.tmp/analyze_win.py`）：L1 有 **2 种**等价铺法、判据只接受 1 种；
   L2 有 **24 种**、判据只接受 1 种；
2. **独立几何模型 + 综合后网表仿真 A/B**：`sim/tb_puzzle_ctrl.py` 新增断言 ⑬⑭⑮。
   修复前 `sim/rounds/puzzle_ctrl/r10.json` = **16 / 17**，断言 ⑭ ❌ ——
   四块锚点 `[(4,2),(2,4),(2,2),(4,4)]`（目标锚点集的一个置换）、四块全锁、
   **并集 == 目标图案（16 格）**，但 **`o_solved = 0`**；
   修复后 `r11.json` = **17 / 17**，断言 ⑭ ✅（`o_solved = 1`、`frm_ok = 1`、`frm_valid = 1`）；
3. **断言 ⑮ 是反例**：四块**原地全锁**（画面不对）→ `o_solved = 0`、`o_all_lock = 1`，
   用来防止把判据放宽成"永远成功"。

**修法**
不给零片编号，直接比**并集**（= 玩家看到的那幅画面）。渲染器本来就一拍算一行的
`cov`（本行被零片覆盖的格子）与 `tgtrow`（目标图案本行），于是
**8 行的 `cov` 都等于 `tgtrow` ⇔ 零片并集 == 目标图案**，判定几乎不花面积：

* 只在**整帧画完**时发布判据（`frm_ok`，帧内出现不匹配则 `frm_bad`）；
* 要求这一帧内 `pos`/`level` 没变过（`pos_frm`/`lvl_frm` 快照 → `frm_valid`），避免一帧混着两种摆法；
* `o_solved = frm_ok and alllock_r`；
* `o_all_lock = alllock_r and frm_valid` —— "全部锁定"对外意味着**判据齐备**，
  最多等一帧（40 ms），避免刚确认最后一块的那一拍拿上一帧的旧判据，把"拼对"又误判成失败；
* `L1_TGT*`/`L2_TGT*` 常量仍保留，但**已不再是判据**，仅用于 `check_geometry.py` 与文档。

**复验**
* 仿真：`puzzle_ctrl` **17 / 17**（断言 ⑬⑭⑮ 见 `docs/03`）；整机 `tb_puzzle_top` **9 / 9** 回归通过；
  **本轮 12 个模块 / 122 条断言全部在同一份修复后的 RTL 上重跑通过**（见 `docs/03` §2、`docs/06` ERR-022）；
* 编译/资源：整机 **1187 / 1270 LE（93%）**（判据换成整帧比较后**面积不升反降**，−15 LE）、
  引脚 **52**、Fmax 仍 **41.39 MHz**、未约束引脚 **0**（均为该轮数字；最新见 ERR-023）；
  `check_keypad_pins.py` mismatches = 0、`check_geometry.py` **ALL CHECKS PASSED**；
* 烧录：**19:25 重新烧录 `puzzle.pof`（随后又复烧一次）**，Erase/Program/Verify 全过，
  0 errors 0 warnings，JTAG ID `0x020A30DD`；
* 上板复测第二关：**已执行，但暴露了两个新缺陷** —— 第一关拼对仍出叉（**ERR-023**）、
  退出重进直接跳第二关（**ERR-024**）。两条均在当日修复并重烧（20:16:18），
  **最终"两关一次走完"的复测仍待现场执行**（清单见 `HANDOFF.md` §7⓪）。

**教训**
1. **判据要判"用户看得见的量"**。B9 的原话是"位置和形状与初始拼图**一致**"——指的是**画面**，
   不是"哪一块放在哪个编号的位置"。把内部编号（锚点）当判据，等于给玩家加了一个
   **画面上根本不存在**的要求。
2. **"有多种等价解"要在设计判据时就数清楚**：`solve_l1.py` 早就报出"恰好 2 组解"，
   当时只把它读成"可解性通过"，没有想到**第二组解会被判失败** ——
   数量证据必须顺着判据再读一遍。
3. **修判据不一定加面积**：4 个 8 位锚点比较器换成 1 个整帧行比较（复用渲染器已有的比较）
   之后整机反而 **−15 LE**。不要预设"改判定一定变贵"。

## ERR-022 · 测试激励陈旧常量导致的"假通过"（陈旧绿）

**现象（全量重跑仿真）**
12 个模块全量重跑时，`game_fsm` 的 `r05` = **14 / 15**：断言 ④"一关对局中 6 个控制键各产生恰好一次
动作脉冲"失败 —— 实测 `o_up`（上）脉冲 = `[]`、`o_right`（右）脉冲 = `[]`，而 `o_down`（下）的脉冲
出现在 **27010 ns**（本是"右"的时刻），`o_move` 只有 2 次（期望 4 次）。

**根因**
键位重排（commit `a1f1c0e`，18:45）之后 `rtl/game_fsm.vhd` 的 `key_of()` 已换成新表
（开始 = 1/KEY14、选择 = 3/KEY16、上 = **10**/KEY7、下 = **2**/KEY15、左 = **5**/KEY10、
右 = **7**/KEY12、确认 = 6/KEY11），但 `sim/tb_game_fsm.py` 里方向键的**原始键号常量**还停在旧值
**4 / 5 / 0 / 2**。在新映射下它们分别被译成 `K_NONE` / `K_LEFT` / `K_NONE` / `K_DOWN` →
"上""右"变成"没按键"，"下"被译成"左"（时间窗错位，实测落在"右"的窗口）。
**这不是 RTL 缺陷，而是测试激励与 RTL 不同步。**

**证据（为什么会"假通过"）**
1. `game_fsm` 上一次通过记录 `r04`（15/15）的时间戳是 **2026-10-08 17:56:56**，
   **早于键位重排提交（18:45）** → 那条绿是**用旧映射测出来的**，对新 RTL 没有效力；
2. 改 `key_of()` 之后**没有人重跑 `game_fsm`**，而汇总脚本 `sim_summary.py` 只读各模块**最新轮次记录**，
   于是"12 个模块全过"的表面结论仍然成立 —— 这就是**陈旧绿**；
3. 重跑（旧常量）立即复现：`r05` 14/15、断言 ④ ❌，失败明细与上面完全一致。

**修法**
把 `sim/tb_game_fsm.py` 的方向键常量改成新键位表 **10 / 2 / 5 / 7**（tb 注释里已写明这段经过）→
重跑 `r06` = **15 / 15**。

**复验**
* `game_fsm` r06 **15 / 15**（断言 ④ 实测 `o_sel@17010 o_up@19010 o_conf@21010 o_down@23010
  o_left@25010 o_right@27010`，`o_move` 共 4 次）；
* 12 个模块全量重跑：**122 / 122 通过，模块数 12**（`python scripts/sim_summary.py` 末尾会打印这一行）；
* 其中 `puzzle_ctrl` r11（17/17）与 `puzzle_top` r11（9/9）是在 **ERR-021 修复后的 RTL** 上跑的 ——
  即修 ERR-022 的过程**没有掩盖 ERR-021 的回归证据**。

**教训**
1. **"最新轮次全过"不等于"当前 RTL 全过"**：汇总前必须核对每条轮次记录的时间戳
   （`rNN.json` 的 `timestamp`）**晚于最后一次接口改动**。改了 `key_of()` / 端口 / 常量表，
   就要重跑所有受影响的 tb。
2. **测试平台也是"代码"**：RTL 改了映射，tb 里引用的键号/锚点/常量同样要跟着改；
   这类不同步**不报错**，只会让断言悄悄失去意义 —— 与 ERR-002"漏配引脚不报错"同源。
3. **反过来也说明断言本身是好的**：修好激励后 r06 的实测值与旧 r04 **完全一致**，
   说明断言是**键位无关**的（只查脉冲时序），失效的只是**激励**。
   定位这类问题要先分清"是激励错了，还是被测对象错了"。
4. **文档纪律**：`docs/03` §2 的"合计全过"必须与各模块轮次记录**逐条对得上**，
   并在表下写明"每个数字来自哪一轮、哪一时间戳"。

# 第 5 阶段：上板复测暴露的两个缺陷（ERR-023 / ERR-024）+ 三处激励缺陷（ERR-025）

> 背景：ERR-021 修好并重烧（19:25）后做上板复测，用户原话：
> **"第一关拼好后确认，然后显示错误；我退出后重新进入后直接又跳入了第二关。"**

## ERR-023 · 对局态把目标图案置零，害死了 ERR-021 的新判据

**现象（上板原话）**
"第一关拼好了、确认，然后显示错误（出叉）。"

**根因**
`rtl/puzzle_top.vhd` 原来把喂给引擎的目标图案在对局态置零：

```vhdl
tgt_play <= tgt_mask when (state = S_PREVIEW or state = S_SELF_TEST) else (others => '0');
```

这行是当年为 **ERR-013**（"别让红色虚影盖住零片"）加的。而 **ERR-021** 的成功判据是
"零片并集 == `i_target`" —— `i_target` 在对局态为 0，**该判据永远不可能成立**，
所以第一关拼得再对，按确认也只会判负。**这就是 ERR-021 的修复"上板不生效"的原因。**

**定位过程**
1. 先看**模块级**仿真：`puzzle_ctrl` r11/r12 都是 **17 / 17** —— "判据本身没问题"；
2. 于是**往上走一层**：读 `puzzle_top` 的引擎例化，发现 `i_target` 接的是 `tgt_play` 而不是
   `tgt_mask`，而 `tgt_play` 在对局态恒 0 → 一眼锁定；
3. 再用**整机端到端**（真实矩阵按键）写断言 ⑩ 复现：修复前 `o_state=5`（失败），修复后 `o_state=2`。

**证据（可执行 A/B）**
* `sim/rounds/puzzle_top/r12.json`（修复前）**8 / 12**：断言 ⑩ ❌ —— 真实按键把三块**准确**拼回目标
  锚点（`pos=0x22324300`、`locked=0111`）后 1 ms，状态机是 **5（失败）** 而不是 **2（第二关预览）**，
  与上板"拼好了仍出叉"完全一致；同轮 ⑥ ❌ 暴露了 tb 的 SW7 激励缺陷（见 ERR-025）；
* `sim/rounds/puzzle_top/r13.json` **11 / 12**（复现轮）：⑩⑪ ✅（ERR-023 修复生效）、⑥ ✅，
  ⑫ ❌ 第三场景状态序列缺了开头的"自检"（观察窗起点问题，属 tb，见 ERR-025）；
* `sim/rounds/puzzle_top/r14.json`（修复后）**12 / 12**：⑩ ✅（1 ms 后 `o_state=2`、`o_level=1`）、
  ⑪ ✅（第二关四块摆成目标锚点集的**置换** `0x42242244`、`locked=1111` → `o_state=4` 胜利）、
  ⑫ ✅ 序列 = 自检 → 待机 → 预览 → 对局 → 预览 → 对局 → 胜利（真实按键连过两关）；
* 引擎侧：`sim/rounds/puzzle_ctrl/r12.json` **17 / 17**，断言 ⑧ 改为"逐格比对**不含鬼影**的着色模型，
  且未覆盖的目标格子必须不亮"（实测未覆盖目标格 11 个、被点亮 **0** 个）。

**修法**
1. `puzzle_top`：**`i_target` 恒接真实目标图案 `tgt_mask`**（判据需要它）；
2. `puzzle_ctrl`：**不再画目标鬼影** —— `redrow := cov and (not selrow)`，把"对局态不能有红色虚影"
   （ERR-013）从"顶层置零"改由**引擎自己保证**。引擎帧只在 `S_PLAYING` 显示，
   其他状态由顶层显示图案/胜负画面，所以那段鬼影逻辑本来就是**靠置零活着的死代码**；
3. 预览仍由顶层用 `prev_row` 显示完整图案 → **对局画面与以前完全一致**（只有零片、无虚影）。

**复验**
* 整机 `r14` **12 / 12**；`puzzle_ctrl` `r12` **17 / 17**；
* 编译/资源：整机 **1191 / 1270 LE（94%）**、引脚 **52**、Fmax **41.39 MHz**、未约束引脚 **0**；
  `check_keypad_pins.py` mismatches = 0、`check_geometry.py` **ALL CHECKS PASSED**；
* 烧录：**20:16:18 重烧 `puzzle.pof`**，Erase/Program/Verify 全过，0 errors / 0 warnings，
  JTAG ID `0x020A30DD`；
* 上板"两关一次走完"复测：**待现场执行**（清单见 `HANDOFF.md` §7⓪）。

**教训**
1. **判据依赖的输入，必须在所有状态下都真的喂进去。** 模块级 tb 恒给真实目标图案，
   于是"顶层在某个状态下把它置零"完全被掩盖 —— **模块级全绿 ≠ 系统级可用**。
2. **"当年为了绕过一个现象"的补丁，会在语义变化后变成缺陷。** 顶层置零是 ERR-013 的临时解法；
   ERR-021 把判据建立在 `i_target` 上之后，它立刻变成致命错误。
   → **改动判据时，必须回头审计"这个输入的所有来源、所有状态"。**
3. **端到端（真实按键）是唯一与上板等价的证据**：模块级、甚至整机里"直连信号"的激励，
   都可能掩盖顶层接线问题。

## ERR-024 · 新一局开头拿上一局的残留状态判决

**现象（上板原话）**
"我退出后重新进入后直接又跳入了第二关。"

**根因**
`puzzle_ctrl` 的 `locked/pos` **只在散落（`i_go`）时清零**。于是刚进 `S_PLAYING` 的头一两拍，
引擎里还是**上一局**的状态（全锁定 + 上一局的拼法）；而 `game_fsm` **无条件**采信
`i_solved`/`i_all_lock`：

* 上一局拼错了但已全锁 → 新一局刚按开始就**判负**（还没散落就出叉）；
* 上一局拼对了 → 新一局刚开局就**"过关"**、`level` 变 1 回到预览 → **直接跳进第二关**。

**定位过程**
1. "退出重进直接跳关"指向**跨局残留**：先看 `puzzle_ctrl` 里 `locked/pos` 的复位条件
   （只有 `i_go` 清），再看 `game_fsm` 的判决分支（无条件采信）→ 可疑窗口只有"开局后一两拍"；
2. 写断言 ⑯⑰ 把这个窗口**钉成可失败判据**：故意让上一局的 `i_solved`/`i_all_lock` 残留到
   新一局开始之后，而 `i_shuf_busy` 晚 2 个时钟才起来（真实引擎要等"散落请求"那一两拍）。

**证据（可执行 A/B）**
* `sim/rounds/game_fsm/r07.json`（修复前）**15 / 17**：⑯ ❌ 对局开始后 3 拍就已经是 **5（失败）**、
  首次判负 **138030 ns**；⑰ ❌ 对局开始后 4 拍就已经是 **2（预览）**且 `o_level=1`、跳转 **152030 ns**
  —— 都在散落之前；
* `sim/rounds/game_fsm/r08.json` **12 / 17**：暴露的是 **tb 模型缺漏**（不是 RTL）—— tb 只给 6 个对局中的
  **2 个**建了散落忙窗，而真实引擎**每一局**都会散落，于是 ⑨⑩⑪⑬⑰ 被拖挂。
  **这一轮如实保留**：它是"tb 模型必须跟着 RTL 判据升级"的证据（见 ERR-025）；
* `sim/rounds/game_fsm/r09.json`（修复后）**17 / 17**：⑯ 首次判负 **140070 ns**（晚于散落结束 140060）、
  `o_go` 每局一次共 **6 次**；⑰ 进第二关预览 **154070 ns**（晚于 154060）、此刻 `o_level=1`。

**修法**
`rtl/game_fsm.vhd` 新增 **`shuf_seen`**（本局是否见过散落忙态）：

```vhdl
if (st /= S_PLAYING) then      shuf_seen <= '0';
elsif (i_shuf_busy = '1') then shuf_seen <= '1'; end if;
```

两条判决分支与胜负音效都要求 **`shuf_seen = '1'` 且 `i_shuf_busy = '0'`**（引擎空闲）——
**判决只在本局散落跑过之后才生效**。

**复验**
* `game_fsm` `r09` **17 / 17**；整机 `puzzle_top` `r14` **12 / 12**（断言 ⑫ 的序列里
  "预览 → 对局 → 胜利"连续出现，且没有"还没散落就判胜/判负"的跳变）；
* 资源：+1 位 `shuf_seen` 及其门控；整机 **1191 LE（94%）**（与 ERR-023 的去鬼影合计 **+4 LE**），
  Fmax **41.39 MHz** 不变；
* 与 ERR-023 **同一次编译/烧录**（20:16:18）。

**教训**
1. **判决必须先确认"本局"的前置条件已经发生。** "清零"是懒惰的（只在某个事件发生时清），
   **"刚开局的一两拍"就是这类残留状态的窗口**；判据必须带一个"本局已进入正题"的门控。
2. **状态机的输入永远是"可能过期"的**：接口上的 `i_solved` 只是一个电平，它的**时间语义**
   （属于哪一局）由产生方与消费方共同负责 —— 消费方不能假设它已经属于本局。
3. **两个现象 ≠ 一个根因**：上板一句话里其实藏着 ERR-023（拼对判负）与 ERR-024（跳过第一关）两条，
   一个在顶层、一个在状态机。**先把现象拆开，再各自定位。**

> 按本文件既有结构单列为 **ERR-025**（激励类）。它们全部由**新断言或离线核对**抓出来。

**现象、根因与修法**

| # | 现象 | 根因 | 发现方式 | 修法 |

* 第 3 条修好后：`game_fsm` ⑯⑰ ✅（`r09` **17 / 17**）；
* 第 4 条修好后：`puzzle_top` 断言 ⑫ ✅（`r14` 序列含开头的"自检"）；

1. **测试平台的"激励"同样要能自查。** 断言能抓出"激励被吃掉"（第 1 条）、"忙窗缺漏"（第 3 条）

   删掉它们就等于删掉这两条教训。

## 6.4 ERR-026 · tb 时间窗基准选错导致误报（测试类）

**现象**
新增断言 ⑬⑭ 后，`sim/rounds/puzzle_top/r15.json` = **12 / 14**：⑬⑭ 都报
"**仿真窗口内没有进入胜利状态**"，而同一轮的 ⑩⑪（进第二关 / 进胜利）都是 ✅ ——
即"胜利其实到了，只是断言没在窗口里找到它"。

**根因**
⑬⑭ 里"找胜利跳变"的时间窗写成了 `t > T_L2_CONF`（= 最后一次确认按下 + 24 轮）。
但按键是**按下后第 16~17 轮才被消抖接受**的，判决还要再晚一个整帧（64 us），
所以真正进 `S_WIN` 的时刻比 `T_L2_CONF` **早几十微秒** → 窗口起点太晚，把事件排除在外。

**修法**：窗口起点改为 `t > T_SW_ON2`（第三场景开始）—— 事件必然落在其后的仿真里。
改后 `r16` = **14 / 14**。

**复验**：`r16` ⑬ ✅、⑭ ✅；上一轮 `r15` = 12/14 作为**误报证据**保留（见 `docs/03` puzzle_top 小节）。

**教训**
1. **"以某时刻为基准"的窗口，必须核对事件真的落在窗口内**：本条的基准时刻是"按键按下 + 固定轮数"，
   而按键被接受的时刻受**消抖轮数**影响 —— 两个时间基准不同源。
2. **同一轮里"相关断言通过、目标断言失败"是强线索**：⑩⑪ 说胜利到了、⑬⑭ 说没找到，
   说明问题在**断言窗口**而不是被测对象。
3. **保留失败轮次**：`r15` 的 12/14 与 `r08`/`r13` 一样，是"测试类缺陷"的证据。

# 第 7 阶段：修显示闪烁（扫描 25 Hz → 125 Hz，ERR-027）＋ 两则工具类记录（ERR-028 / ERR-029）

> 背景：2026-10-08 上板反馈——**"点阵和数码管都闪得比较明显"**。这条不是"编码错误"，
> 而是**设计阶段的一个物理假设写错了**（注释里白纸黑字写着"25 Hz 已高于闪烁融合"）。

## ERR-027 · 刷新率只有 25 Hz + 注释里写错的"闪烁融合"假设

**现象（上板原话）**
"点阵和数码管都闪得比较明显。"

**定位过程**
1. **算节拍**：点阵行计数器 `mrow` 走 `tick_200`（5 ms/行）→ 8 行 = **40 ms → 25 Hz 帧刷新**；
   数码管位选（`seg_scan.i_tick`）同样走 `tick_200` → 每位 5 ms → **25 Hz/位**；
   引擎行渲染 `puzzle_ctrl.i_tick` 也是 200 Hz（8 拍一帧）。
2. **查设计里的"刷新率"注释**：`seg_scan` 与 `puzzle_ctrl` 里都写着
   "200 Hz / 8 = 25 Hz，**comfortably above flicker fusion**" ——
   **这个判断本身是错的**：LED 的临界闪烁融合一般要 **> 60 Hz**，25 Hz 明显可见闪。
   → 结论：不是接线/极性问题，是**指标算错**。

**受控实验（"为什么只改一半"的依据）**
| 配置 | 整机 LE | 结论 |
|---|---|---|
| 只把**扫描侧**（`mrow` + `seg_scan.i_tick`）提到 `tick_1k`，引擎保持 `tick_200` | **1188 / 1270（94%）** | ✅ 采用：扫描 **125 Hz**，闪烁消失，**面积零代价** |
| 连**引擎行渲染** `u_puzzle.i_tick` 也提到 `tick_1k` | **1264 / 1270（100%）**，只剩 **6 LE**（**+76 LE**） | ❌ 放弃：闪烁只由**扫描率**（亮度调制）决定，与"画面内容更新率"无关，收益为零 |
| 改回 `tick_200` | **1188（94%）** | 复现"只改扫描就够" |

**修法**
* `puzzle_top`：`mrow` 由 `tick_200` 改 **`tick_1k`**；`u_seg.i_tick` 由 `tick_200` 改 **`tick_1k`**
  → 点阵 8 行 = 8 ms = **125 Hz**、数码管 8 位 = 8 ms = **125 Hz/位**；**占空比仍 1/8，亮度不变**；
* **键盘扫描仍留在 `tick_200`**（消抖 16 轮 = 80 ms 是按 200 Hz 轮定义的，不能动）；
* `clk_gen` 的 `tick_40`（40 Hz）**已不再被任何模块使用**（它当年是为"扫描/渲染同源"加的）；
  **输出保留**（不动 `tb_clk_gen` 的节拍断言），只把注释与 tick 表改成"不再使用"。

**复验**
* 编译/资源：整机 **1188 / 1270 LE（94%）**、**52** 引脚、Fmax **41.39 MHz 不变**、未约束引脚 **0**；
  `check_keypad_pins.py` mismatches = 0、`check_geometry.py` ALL CHECKS PASSED
  （重编译报告见 `docs/05` §1，23:08:52）；
* **扫描率的实测值（从 `r20` 波形直接量出）**：点阵行周期 **1600 ns（仿真）= 1.000 ms（板上）→ 125.0 Hz**；
  数码管位周期同样 **125.0 Hz**；改前（`tick_200`）= **5 ms → 25 Hz**。
  （仿真时钟压缩 **625 倍**：80 kHz 代替 50 MHz，所以 1.6 µs 仿真 = 1 ms 板上；行/位周期 8 ms → 1.6 ms 仿真、5 ms → 1 ms 板上，**正好 5 倍**。）
* 烧录：`puzzle.pof` 生成于 **23:08:53** 并重烧，Erase/Program/Verify 全过、0 errors / 0 warnings；
* 仿真：模块级 tb 不受影响（`seg_scan`/`dot_matrix_scan`/`puzzle_ctrl` 的 tb **自己产生 `i_tick`**，
  与顶层用哪路节拍无关）；整机 `puzzle_top` 新增第四条场景的**失败画面断言 ⑮** → **`r20` = 15 / 15**
  （记录时间 2026-10-08 23:54:08，时长 96632000.0 ns）。
  ⚠️ 中间轮次：`r17` = 13/15（⑬⑭ ❌）是 **tb 观察窗被新增的第四场景污染**（观察窗原来取到 `DURATION`）——
  与 ERR-026 同类，修法是"**观察窗止于胜利态结束** + 第四个场景的开始键挪到窗口之后"，**保留为证据**；
  `r19` 因**同模块并发仿真把波形写坏而作废删除**（见 ERR-028）；
* 上板"不再闪"的最终确认：**随两关复测一起做**（见 `HANDOFF.md` §7⓪）。

**教训**
1. **刷新率这类"人眼指标"必须在设计阶段算清、并写对注释**：25 Hz 的帧率在纸面上"看起来不低"，
   但对 LED 就是可见闪 —— 本项目把错误的判断写进了注释，反而让后人都以为没问题。
   **注释里的判断也可能是错的，要回到物理指标复核。**
2. **改显示性能前先做受控实验量面积代价**："把引擎也提到 1 kHz"听上去更"彻底"，
   实测 **+76 LE（1188 → 1264/1270，只剩 6 LE）** 而收益为零 ——
   **别为了"看起来更对"把 94% 的面积吃光**。
3. **同一个现象要问"它由哪个物理量决定"**：闪烁由**扫描率**（每行/每位被点亮的频率）决定，
   与内容更新率无关；把这两个率分开，才敢"只改一半"。

## ERR-028 · 同一个模块的仿真被并发跑 → 波形互相覆盖（测试/工具类）

**现象**
整机 `puzzle_top` 的中间轮次 **`r19`** 断言数字**完全不可信**：报出"37.5 ms 就进入失败态"、
结算画面实测全 `0xFF` 之类的离奇结果 —— 而同一份 RTL 在 `r16` 上是自洽的。

**根因**
`scripts/sim.py` 的**向量源与结果回写用的是同一个文件** `sim/<模块>.vwf`。
本次把**同一个模块**的两个仿真（`r18` 与 `r19`）**并发**跑了：
两个 `quartus_sim` 进程一个在读向量、一个在回写结果，**互相覆盖** → 波形被写坏，
断言阶段读到的是一份"被两个 run 拼起来"的坏数据。
（`--overwrite_waveform=on` 的设计本身没问题 —— 它保证"激励与结果同文件"，但前提是**同一模块串行**。）

**处置**
* `sim/rounds/puzzle_top/r19.*` **已删除**（坏数据不留档）；
* `puzzle_top` **单独重跑**，最终轮次以 **`r20`** 为准；
* 纪律：**不同模块可以并行（各自的 `.vwf` 不共享）；同一个模块必须串行** ——
  并发前先看"输出路径是否共享"。

**顺带一条好消息 → 单列为 ERR-029**
`scripts/vwf.py` 的 `value_at` / `bus_value_at` 原来**每次查询都重新展开整条节点**
（查询数 × 跳变数 → O(n²)），点阵扫描提到 125 Hz 后 `check` 阶段要跑 **40+ 分钟**；
改成"**编译一次阶梯表 + `bisect`**"后 **8 秒**。详见下面的 **ERR-029**（已复核语义不变）。

**教训**
1. **并行必须按"资源是否共享"划界**：不是"能不能同时跑"，而是"**输出路径是否共享**"。
   本项目已有一次同类教训（ERR-022 的"陈旧绿"）：那次是**同一模块没重跑**，
   这次是**同一模块跑了两次** —— 两个方向都会毁掉判据的可信度。
2. **坏数据要敢删、并写明为什么**：`r19` 如果"将就用来填文档"，整份报告的数字都会被污染；
   **删除 + 记录原因（本条目）**比"保留一个看着像结果的轮次"诚实得多。
3. **验证工具的性能也是工程指标**：`check` 从 40 分钟降到 8 秒是**数量级**改进，
   它直接决定"愿不愿意每轮都跑全套断言"（详见 ERR-029）。

## ERR-029 · `vwf.py` 的查询是 O(n²) → 编译一次阶梯表 + `bisect`（工具类·好消息）

**现象**
点阵扫描从 25 Hz 提到 **125 Hz** 后，`scripts/sim.py` 的 **check 阶段要跑 40+ 分钟**
（`puzzle_top` 整机尤其明显）—— 仿真本身没慢，慢的是**断言阶段的波形查询**。

**根因**
`scripts/vwf.py` 的 `value_at` / `bus_value_at` 实现是"**每次查询都重新展开整条节点**"，
复杂度是 **查询数 × 跳变数 → O(n²)**；而扫描提速后每帧的跳变数增加约 5 倍，
于是"一条查询本来就不便宜 × 更多查询"直接把 check 拖成分钟级。

**修法**
改成 **"把阶梯表编译一次 + `bisect` 二分查找"**：每条节点只解析一次，之后的查询是 O(log n)。

**复验（关键：证明只改性能、不改语义）**
* check 阶段 **40+ 分钟 → 8 秒**；
* 在 **`seg_scan` / `disp_format` / `puzzle_ctrl` / `game_fsm`** 四个模块上
  **逐条复核优化前后的断言结果完全一致**；
* 这三个模块的轮次记录与结论因此**无需改动**（如 `seg_scan` 复核时又跑过一次 check，轮次仍是 r07）。

**教训**
1. **验证工具的性能也是工程指标**：它决定了"愿不愿意每轮都跑全套断言"——
   40 分钟的 check 会让人**跳过验证**，那比慢本身更危险。
2. **性能优化必须配"语义不变"的证据**：本例用"四个模块逐条一致"来证明
   —— 与 RTL 优化一样，**只改写法不改语义**要有可执行对照。
3. **算法改进（O(n²) → O(log n)）比换机器有效**：瓶颈是"重复解析"，不是算力。

## 8.1 改版内容（用户提问触发）

**用户原话**："通关后 DISP7、DISP6 显示 7、5 是什么意思？"

**为什么原来没有语义**：`rtl/disp_format.vhd` 的 `S_WIN` 原样输出 `DISP7='7'`、`DISP6='5'`

both are easy to tell apart from anything else on the panel"，即**只是早期设计为了"和其它状态

而 PDF 只规定 DISP0=关卡号（B3）、DISP7=预览倒计时（B4）、DISP4:DISP3=对局倒计时（B5）、

**用户拍板 A 方案**：胜利显示 **`PASS`**、失败显示 **`FAIL`**（最左四位拼字，其余四位全灭）。

**实现（三处）**：
1. `rtl/puzzle_pkg.vhd` 新增 §9 **DISP 字位码**：`DIG_BLANK=0xF`、`DIG_A=0xA`、`DIG_P=0xB`、

2. `rtl/seg_scan.vhd` 译码表新增 5 个字母段形（`0xA→A`、`0xB→P`、`0xC→S`、`0xD→F`、`0xE→L`），

3. `rtl/disp_format.vhd`：`S_WIN` → DISP7..DISP4 = `P A S S`、`S_FAIL` = `F A I L`，其余位全灭。

## 8.3 ERR-030 · 按"跳变表"取样会漏掉相邻同码的位槽（测试类教训）

**现象**
新增断言 ⑪ 的第一版读出 `'PA?S'`：W10 里**第二个 `'S'` 那一位被漏掉**，反解结果是 `????`/`PA?S`。

**根因**
第一版按 `o_seg` 的**跳变表**给每位取样（"跳变即换位"）。但 `PASS` 里的两个 `'S'` **段码相同**
（`0x6D`），中间那一位**不产生跳变** → 跳变表里没有边界 → 那个位槽被跳过。

**修法**
改成"**按位槽中点取样**"：位槽边界从 **`o_cat`（位选）的转移表**取，然后在每个位槽的中点采 `o_seg`。
改后 `seg_scan` **`r12` = 11 / 11**（此前的 `r09`/`r10`/`r11` 均 **10 / 11**，**全部保留**：
`r09` 读出 `'????'`、`r10` 读出 `'1110?12'`、`r11` 读出 **`'PA?S'`**）。

**教训**
1. **查波形要按"时间槽"取样，不能只看跳变**：跳变表隐含"相邻信号必不同"的假设，
   而"拼字"这类内容**天然会出现相邻同码**（`S S`、`A A`…）。
2. **同一条教训在整机层面也一样**：`puzzle_top` 的 ⑬⑮ 校验数码管时，从位选（`o_cat`）取槽边界，
   而不是从段码跳变推断。
3. **"随手挑的记号"要在报告里交代**：能自解释的更好 —— 本项目 `75`/`00` 被用户一问就露馅，
   改成 `PASS`/`FAIL` 后**不用解释**。

> ⚠️ **保留历史**：`seg_scan` 的第一版取样（按跳变）与它读出的 `'????'`/`'1110?12'`/`'PA?S'`
> （`r09`/`r10`/`r11`）都记在本条目里，
> 不删 —— 它是"测试假设错误"的又一条实例（与 ERR-022/025/026/028 同类）。
