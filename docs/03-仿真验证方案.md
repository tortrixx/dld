## 1. 为什么是这样一套仿真（工具链的现实约束）

本机**没有 ModelSim / GHDL**，只有 **Quartus II 9.1 内置仿真器**。它有三个硬约束，
决定了整套方案的样子：

| 约束 | 后果 |
|---|---|
| 仿的是**综合后功能网表**，不支持 VHDL testbench / `assert` | 断言只能写在**外面**：解析仿真结果、用 Python 判据逐条比对 |
| 激励**必须**来自 `.vwf` 向量波形文件 | 要自动化就得**自己生成 .vwf、自己解析 .vwf** |
| 仿真器只覆盖"被声明过的节点" | ".vwf 里必须含中间信号"这条课件要求，靠把内部信号按 `BURIED` 声明进 `.vwf` 来满足 |

于是本工程写了两个基础设施（约 1200 行 Python）：

* `scripts/vwf.py` —— `.vwf` 的**生成器 + 解析器**（`Builder` 写激励，`parse` 读结果）
* `scripts/sim.py` —— 仿真驱动：
  `python scripts/sim.py run <模块>`
  ① 生成激励 → ② 在 `.tmp/sim_<模块>/` 建**隔离工程**（RTL 副本 + 该目录自己的 `.qsf`）
  → ③ `quartus_map --generate_functional_sim_netlist` → ④ `quartus_sim`
  → ⑤ 解析回写的结果 → ⑥ 跑 tb 里的断言 → ⑦ 出波形图 → ⑧ 写轮次记录

> **仓库全程只读**：所有仿真都在 `.tmp/` 的副本里编译，`rtl/` 与 `quartus/puzzle.qsf`
> 一个字节都不会被临时改动 —— 早期"改项目文件再还原"的做法出过两次事故
> （引脚约束被截断、分频常量漏还原），这条纪律是那两次事故换来的。

### 1.1 每个模块的 tb 契约

`sim/tb_<模块>.py` 提供：

| 名称 | 作用 |
|---|---|
| `DURATION` / `GRID_PERIOD` | 激励时长与网格 |
| `OBSERVE` | 观测点清单（**含中间信号**；缺一即报错，逼着你把内部信号放进波形） |
| `build(b)` | 声明节点 + 驱动激励（`b.clock/segments/bus_segments/output_*`） |
| `check(vf)` | 解析波形做断言，返回 `[(名称, 是否通过, 实测说明), ...]` |
| `RTL_PATCHES`（可选） | 只作用于隔离副本的常量替换（用于时间压缩），**会被记进轮次记录** |

### 1.2 判据是怎么写的（这一条决定这 25 分是不是白拿）

**不写"看着像对"的断言**。每条判据都要求能**真正失败**，做法是：

1. **独立参考模型**：例如 `rng_lfsr` 的 255 拍序列是在 Python 里按
   x⁸+x⁶+x⁵+x⁴+1 自己推演出来的，与 RTL 逐拍比对；`puzzle_ctrl` 的重叠/越界/着色
   是在 Python 里按「bit = 8×行+列」重建零片格子后**逐格**算出来的。
2. **把"物理"算出来**：4x4 矩阵键盘的扫描相序是确定的，所以"按下 (行,列) 时行线
   什么时候该为低"可以精确算出来 → tb 按这个物理模型生成 `kp_row` 波形，
   **是真的被扫描器识别**，而不是绕过输入通道直接给键码。
3. **按需求（B1~B11）对时序下判据**：例如"预览结束进对局时 `o_time` 必须被加载为
   30"就是 B5 的判据，也正是 ERR-005 的回归判据。
4. **时间压缩不改变需求秒数**：整机场景把 `CLK_HZ` 从 50 MHz 改成 80 kHz
   （只作用于隔离副本），但**分频比一个都没改** —— 断言里判的是"几个 1 Hz 节拍"
   而不是纳秒，所以"自检 2 秒 / 预览 5 秒 / 限时 30 秒"这些需求值从未被放宽。

> （commit `a1f1c0e`，18:45）之后**漏改**（旧值 4/5/0/2，新表是 10/2/5/7），而该模块上一次记录 `r04`
> 的时间戳是 **17:56:56（早于重排）** —— 于是汇总脚本读到"15/15 全过"，看起来一切正常，
> 实际是**用旧常量测新映射**；重跑即露出真相（r05 14/15，断言 ④ ❌），改对常量后 r06 恢复 15/15。
> **结论：改了 `key_of()` 或任何跨模块接口之后，必须重跑受影响的 tb**；
> 只看"最新轮次全过"会被陈旧绿骗过 —— 判据必须是**轮次时间戳晚于最后一次接口改动**。

> 断言的**风格**说明：每个模块里都至少有一条"自检型"断言（例如 `piece_rom` 的
> 形状面积守恒、`puzzle_ctrl` 的零片格数 3/6/12），用来防止 **tb 自己把数据抄错** ——
> 测试基准本身的正确性和被测对象同样重要。

## 5. 仿真抓到并修掉的 4 个真缺陷（ERR-016~019，**这一节是这 25 分之外最有价值的产出**）

仿真之前，整机在板子上"看起来能跑"：自检亮、待机对、预览出完整图案、散落有零片、
选择能红/绿切换。**但仿真逐格算账之后，发现 4 个看波形看不出来的真缺陷**
（详见 `docs/06` ERR-016 / ERR-017 / ERR-018a / ERR-019）：

| 编号 | 缺陷 | 为什么"上板看起来是好的" | 仿真是怎么抓到的 |
|---|---|---|---|
| ERR-016 | 重叠检查的**行号流水没对齐**（候选行晚一拍，却拿当前行去比邻居） | 散落仍会出现零片，只是位置可能重叠 | `tb_puzzle_ctrl` 用独立几何模型逐格算"两两不重叠"，直接抓到两块叠在同一格 |
| ERR-017 | 散落时"自己"的掩码用了 `sel`（散落期间恒 0）而不是 `sh_k` | 同上；还会误拒合法落位 | 同上：确定性散落（rnd 恒 0）时第 3 块**正好落在第 1 块身上** |
| ERR-018a | 散落**重试不再抽新候选**（16 次"尝试"其实是同一个位置） | 首候选一冲突就必然走确定性回退，回退锚点又不查重叠 | 波形里 `chk_pos` 连续 16 次完全相同 —— 一眼就能看出"拒绝采样没有重采样" |
| ERR-019 | `srl8` 把整行往**左**移，而"按锚点列摆放"要求往**右**移 | 4×3 矩形预览是**直接取图案常量**画的，不经过这个移位，所以预览看起来完全正常 | `tb_puzzle_ctrl` 断言 ⑧ 逐格比对着色：选中的零片**一格都没画出来** |

ERR-019 尤其说明问题：同一份"看起来正常"的板级现象背后，**游戏中的零片其实画错了
列、并从左边界丢格子**（1x3 横条在锚点列 2 时只画出一个点）。这条在板子上要靠
"数格子"才能发现，仿真里一条逐格断言就钉死了。

> ⚠️ 顺带记一笔（`AI_LOG.md` 里也记了）：这个移位方向**此前被人工"核实"过并驳回**。
> 当时的推理是"`v := '0' & r(7 downto 1)` 即 v(c)=r(c-1)，正是向右移" —— 这一步
> 推理错了：`'0' & r(7 downto 1)` 是 v(c)=r(c+1)，位号变小 = 面板上向左移。
> **结论：人工"验算"也会错；最终判据必须是可执行的行为比对。**

### 5.1 修完之后的代价（如实记录）

修正 ERR-019 之后，**编译面积从 958 LE 涨到 1201 LE（95%）**，Fmax 从 42.24 MHz
降到 41.39 MHz。原因不是代码写得更啰嗦，而是：

* 旧的（错的）左移会把零片形状里**低列**的格子推出边界 → 综合器能把锚点列 ≥ 3 的
  那几路输出**常量折叠**掉，一整片移位网络被剪掉；
* 正确的右移必须把格子搬到高列，**每一个锚点列都真的要用** → 无法折叠。

这条也一并写进 `docs/05` 与报告"总结"：**"面积小"有时是 bug 的副产品**。

> ⚠️ **2026-10-08 后续更正**：上面的 1201 LE（95%）是**修 ERR-019 那一轮**的数字。
> 之后修 **ERR-021**（成功判据由"4 个 8 位锚点比较器"换成"1 个 8 位整帧比较 + 快照寄存器"），
> 重编译实测 **1187 / 1270 LE（93%）**、Fmax 仍 **41.39 MHz**、52 引脚 —— **面积不升反降**。
> 当前数字一律以 `docs/05` §1 为准。

### 5.2 ERR-021（上板现象 → 仿真复现 → 修复回归）

### 5.3 ERR-023（对局态目标被置零 → ERR-021 的判据永不成立）

> 来源：ERR-021 修复并重烧（19:25）后的**上板复测**——用户原话："第一关拼好后确认，然后显示错误。"
> 模块级仿真（`tb_puzzle_ctrl`）**掩盖**了它：那里 `i_target` 恒为真实图案。

| 环节 | 内容 |
|---|---|
| 上板现象 | 第一关把三块拼成与预览一致的图案、逐块确认 → 仍显示失败图案（出叉） |
| 读顶层接线 | `rtl/puzzle_top.vhd` 原来 `tgt_play <= tgt_mask when (S_PREVIEW/S_SELF_TEST) else (others => '0')` —— **对局态把喂给引擎的 `i_target` 置零**（当年为 ERR-013"别让红色虚影盖住零片"）。而 ERR-021 的判据是"零片并集 == `i_target`" → **永远不可能成立** |

| 引擎侧判据 | `puzzle_ctrl` 断言 ⑧ 改写为"逐格比对**不含鬼影**的着色模型 + 未覆盖目标格必须不亮"：`r12.json` **17 / 17**，实测未覆盖目标格 11 个、其中被点亮 **0** 个 |
| 同轮暴露的激励缺陷 | `tb_puzzle_top` 的 SW7 用 `_tl()` 拼了三段**首尾相接**的区间，而 `_tl` 是"事件排序"实现、同一时刻"恢复 1"排在后面 → 0 那段被吃掉，断言 ⑥ 当场报"点阵仍亮 12 格"（r12 ❌）。见 §5.5 |

`puzzle_ctrl`，于是"顶层在对局态把它置零"完全被掩盖；只有**整机端到端（走真实按键）**才复现出上板现象。

### 5.4 ERR-024（新一局开头拿上一局的残留状态判决）

| 环节 | 内容 |
|---|---|
| 上板现象 | 用户原话后半句："我退出后重新进入后直接又跳入了第二关。" |
| 根因 | `puzzle_ctrl` 的 `locked/pos` **只在散落（`i_go`）时清零**；刚进 `S_PLAYING` 的一两拍里引擎仍是**上一局**的状态（全锁定 + 上一局拼法），而 `game_fsm` 无条件采信 `i_solved`/`i_all_lock` → ① 上一局拼错但已全锁 → 新一局刚开局就判负；② 上一局拼对 → 新一局刚开局就"过关"、直接跳第二关 |
| 修法 | `game_fsm` 新增 **`shuf_seen`**（本局是否见过散落忙态）：两条判决分支与胜负音效都要求 `shuf_seen='1'` **且** `i_shuf_busy='0'`（引擎空闲）；即判决只在本局散落跑过之后才生效 |
| 模块 A/B | `r07.json` **15 / 17**（⑯ ❌ 对局开始后 3 拍已是 5 失败、首次判负 138030 ns；⑰ ❌ 4 拍已是 2 预览、跳转 152030 ns —— 都在散落之前）→ `r08.json` **12 / 17**（暴露的是 **tb 模型缺漏**、不是 RTL：只给 6 局中的 2 局建了散落忙窗，⑨⑩⑪⑬⑰ 被拖挂，见 §5.5）→ `r09.json` **17 / 17**（⑯ 首次判负 140070 ns > 散落结束 140060；⑰ 进第二关预览 154070 ns > 154060、此刻 `o_level=1`；`o_go` 每局一次共 6 次） |
| 整机回归 | `puzzle_top` 断言 ⑫ 的序列里"预览 → 对局 → 胜利"连续出现，整机没有"还没散落就判胜/判负"的跳变（r14 ✅） |
| 资源/烧录 | 与 ERR-023 同一次编译：**1191 / 1270 LE（94%）**（+4 LE：去鬼影 + 1 位 `shuf_seen`），Fmax **41.39 MHz** 不变 |

**教训**：**判决必须先确认"本局"的前置条件已经发生。** 状态清零是"懒惰"的（只在某个事件时清），
"刚开局的一两拍"就是这类残留状态的窗口；判据必须带一个"本局已进入正题"的门控。

### 5.5 同一轮修掉的四处**测试激励**缺陷（ERR-025，激励类）

> 这四处都**不是 RTL 缺陷**，但会让断言失效或静默丢激励 —— 与 ERR-022 同类，
> 因此按既有结构单列为 **ERR-025**（详见 `docs/06`）。

| # | 症状 | 根因 | 发现方式 | 修法 |
|---|---|---|---|---|
| 1 | 断言 ⑥（SW7=0 应全灭）报"点阵仍亮 12 格" | `tb_puzzle_top` 的 SW7 用 `_tl()` 拼了三段**首尾相接**的区间；该 `_tl` 按"事件排序"，同一时刻"恢复默认 1"排在后面 → **0 那一段被吃掉**，SW7 其实一直是 1 | 新断言 ⑥ 当场失败（`r12` ❌） | 直接给 `(时长, 值)` 序列，不再用相邻区间拼接 |
| 2 | 同一个键连按两次时，第二次**被静默丢掉** | `keypad_scan` 消抖是"连续 16 轮不同才改 stable"，松开窗口必须 > 16 轮；而按键计划按"当前命令与上一条是否同键"留间隔（差一位），`down,down` 之间只留 25 轮（松开 3 轮） | 离线核对脚本 `.tmp/plan_top.py` 把 42 次按键的排期打印出来（它还离线验证了走法、最终锚点与键位映射） | 同键间隔 `GAP_SAME=44`（松开 22 轮） |
| 3 | `game_fsm` 的 `r08` = **12/17** | tb 只给 6 个对局中的 2 个建了散落忙窗，而真实引擎**每一局**都会散落（ERR-024 要求"本局见过散落"）→ ⑨⑩⑪⑬⑰ 被拖挂 | 重跑断言 ⑨⑩⑪⑬⑰ 集体失败 | 给 **6 个对局各建一个忙窗**（`SHUF_BUSY_WINS` 6 条），更贴近真实时序 |
| 4 | `puzzle_top` 的 `r13` = **11/12**（⑫ ❌：第三场景序列缺开头的"自检"） | ⑫ 的观察窗起点用了 `T_SW_ON2`（拨回来那一刻）；但 SW7=0 期间状态机就停在"自检"，拨回来不会再产生跳变 | 断言 ⑫ 失败后回读 tb 取窗代码 | 观察窗改为从 **`T_SW_OFF`**（拨下去那一刻）起数 |

**教训**：**测试平台的"激励"同样要能自查。** 断言能抓出"激励被吃掉"（第 1 条）、
"忙窗缺漏"（第 3 条）、"观察窗起点"（第 4 条）；而"按键被静默丢掉"要靠**离线把排期打印出来核对**（第 2 条）——
写激励时不能只看"走法对不对"，还要看"**时间表够不够、窗口取在哪个时刻**"。
`r08`（12/17）与 `r13`（11/12）都作为**失败证据**保留，不删。

## 6. 本方案的已知局限（不含糊）

| 局限 | 说明 |
|---|---|
| 没有第三方仿真器交叉验证 | 本机只有 Quartus 内置仿真器；它的功能仿真**不包含器件延时**，所以"时序"类结论（Fmax / 关键路径）由 TimeQuest 的报告支撑，不来自本仿真 |
| 整机场景压缩了时钟 | `CLK_HZ` 在隔离副本里改为 80 kHz（分频比不变）。真实 50 MHz 下跑完"2 s + 5 s + 对局"要上亿拍，仿真不可行；**需求里的秒数没有被改**，只改每秒钟的时钟数 |
| `piece_rom` 在功能仿真网表里没有内部节点 | 它是纯常量选择 ROM，综合后只剩端口（`.tmp/sim_piece_rom/output_files/puzzle.sim.rpt` 的覆盖率表可查）→ 只能用聚合端口的分解通道当"中间信号" |
| 顶层多数内部信号需要层次名 | 顶层自己的信号大多被优化进子模块，要用 `实例标签|信号名`（如 `u_fsm|st`、`u_puzzle|pos`）才能声明；这个名字格式是用探针实测确定的 |
| ERR-018b 未修 | 16 次随机尝试全失败后走的**硬编码回退锚点仍不做重叠检查**。ERR-018a 修好后它只在"随机源连续 16 次给出冲突候选"时才可能触发（真实 LFSR 每次尝试都翻新，概率约 1e-7 量级），本轮**如实记录、未修复**；`tb_puzzle_ctrl` 的断言 ⑯ 用极端激励把它复现出来留档 |
| 图案库只覆盖第三关的两种图案 | A2 的图案随机选择**只加在第三关**（第一关按 B4 固定图 4-1、第二关按 B10 固定 PAT3）；4 幅图案里整机只端到端验了 **2 幅**（图案 0 = 模式 A `r29`、图案 2 = 模式 B `r30`），图案 1/3 由 `tb_pattern_rom` ④ 逐 (level,pat,row) 精确比对 + `check_geometry.py` 逐幅穷举可铺性覆盖，**不走整机**（省两轮 ~26 min 仿真）；判据代码本身与图案无关（ERR-021 的整帧比较） |
| 消抖时长的"文档—代码"一致性靠断言守 | ERR-031 说明注释里的时序算术**会错**。现在 `tb_keypad_scan` 断言 ⑨ 把 4 轮/9T/63T 钉死：改 `DEBOUNCE_MAX` 而忘了同步文档/测试台会立刻挂 |
| ⭐ 音效的**听感**无法被仿真验证 | 仿真只能验"**发的是哪个音效码**"（`u_fsm\|sound_p`）、"**这一步响不响**"（`u_buzz\|on_now`）与"**响了几个连续区间**"（㉒ 数"恰好一声"）。**"好不好听""连不连贯"仍然只能上板听** —— 第 16 工作阶段的 ERR-050（照抄原谱休止 ⇒ 56% 静音）就是仿真全绿、板上才发现的问题。⚠️ 与之相对，**"占空比/连奏"已经被写成了可断言指标**（音乐句 16 步全发声、提示音允许休止、FAIL 句尾 3 步留白），由 `tb_buzzer_ctrl` 的设计规则自检守住 |
| ⭐ ERR-051 的"第一个半步"残余无法在本仿真里消除 | 自检窗口起点（SW7 拉高）与 `tick_4hz` 网格不同相，**第一个旋律步只有 (0,250] ms**；发声步落在它上面（概率 1/8）时这一声偏短。这是**有意的取舍**（彻底消掉会让窗口变 2.25 s、违反 B2 的"2 秒"）—— 见 `docs/06` §18.1.7。仿真断言 ㉒ 验的是"**恰好一声**"，**验不了"这一声够不够长"** |
| ⭐ `tb_puzzle_top` 的音效断言只在**模式 A/B 两个场景**上跑 | 音效码的**全码表**覆盖仍靠 `tb_buzzer_ctrl`（16 个码逐句）与 `tb_game_fsm`（㉓~㉗）；整机 ⑱~㉒ 证的是"**这条链路真的通了**"，不是"16 个码都验过"。两类证据**互补**，引用时要说清是哪一类 |
| ⭐ **轮次记录里没有 RTL 哈希**（收尾审查发现） | `rNN.json` 只有 `module/round/timestamp/passed/total/all_pass/assertions/rtl_patches/duration_ns` —— **不存任何文件哈希**，所以文档里引用的 ad-hoc `SHA256` **无法复核**（还受 CRLF/LF 双版本影响）。**改进项 = 落盘时记 `git hash-object`**（`docs/06` §17.12 / §17.13） |
| ⭐ **"复核"默认不落盘**（ERR-052 之后的行为） | `sim.py check <mod>` **只读**（不写轮次记录、不重画 SVG）；要落盘必须显式 `--record`。⚠️ 因此"某轮记录的时间戳"**不会**因为一次 `check` 而刷新 —— 这是有意设计（见 §7） |

> ⭐ **收尾审查的另一条正结果（可复现性证据）**：**拿现在的 tb 对已提交的波形重跑 `check()`，
> 复现出记录里的断言集合**（11 个非整机模块合计 **156/156**）——
> 说明轮次记录里的断言**确实来自这些波形**，不是事后抄的。
